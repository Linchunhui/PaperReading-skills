01

问题 01

状态应该放在哪里？

当前世界、未解缺口和全文日志分层保存。

长任务失败常因关键决定埋在长日志里；删掉旧记录又可能丢掉尚未完成的条件。运行状态必须区分观察、推断、目标、待办和已执行动作。

同一份紧凑上下文不必包含全部历史；外层可靠保存全文，内层只渲染当前决策所需结构，但任何摘要都应可回到来源。

教学例：修复一个项目并运行测试。工具在提交结果后回执丢失；Agent需要知道哪一步完成、哪些只是计划、下一步缺什么证据。

Beyond Memory: Harnessing Long-Horizon Agents with Explicit Belief States

2026-10-01

维护当前状态及未完成缺口，检测停滞再恢复。

  1. 历史摘要记录发生过什么，PoS进一步维护当前世界W、目标G、未知信息缺口ΔE和待实现目标缺口ΔA；实体、状态及关系带来源、置信度和支持证据。
  2. 每步选择一个active gap指导行动。得到新观察后先产生候选信念，再由Belief Sentinel检查内部冲突和与观察不符的外部冲突，修订后才能提交为下一状态。
  3. 接教学例：“测试没通过”是已知观察；“哪个文件触发错误”是信息缺口；“修复并重跑测试”是行动缺口。若多轮只反复打印同一日志且两类缺口均未缩小，就触发停滞诊断与恢复约束。
  4. 恢复不是简单重试：框架区分停滞的动态模式和阻塞缺口类型，组合约束引导下一步。语义信念检查依然由同一骨干LLM完成，不是形式化真实性证明。

02

问题 02

怎样组织工具协作？

把计划变成工具契约、可检查工件和版本化技能。

工具的名字与描述只负责发现；输入schema、权限、隔离、输出格式及失败语义决定它实际怎样执行。返回字符串成功也不等于产物符合任务。

多Agent会共享文件、测试和任务状态；应定义工件所有权、分支隔离、汇总顺序与回归测试。技能版本必须连同依赖、接口、证据和验收一起管理。

读图前的算例 · 教学示意

沿用项目：根因Agent只读并写诊断，修复Agent改隔离副本，复核Agent跑测试；协调者合并工件，按动作ID和版本号记录。

Code as Agent Harness

2026-05-18

把计划、工具、技能和协作落实为可执行工件。

  1. 这是一篇综述，以三层组织运行框架：代码作为推理/动作/环境接口；规划、记忆、工具、控制与优化机制；多Agent通过仓库、测试、轨迹及工作流共享状态。它本身不提出一个统一实验系统。
  2. 代码工件的作用是让意图能执行、过程能观察、状态能持续。API schema、配置、测试、回放轨迹和技能脚本各有角色；一段自然语言计划仍需工具接口和验收条件才能改变环境。
  3. 接教学例：计划指定需改函数与回归测试，工具按schema校验参数并在隔离副本执行；技能包含脚本、输入输出、依赖和测试，版本更新要重放代表轨迹。单个成功测试只是传感器之一，不能证明任务全部完成。
  4. 多Agent可分别查根因、修复与复核，但共享仓库必须解决谁修改哪个文件、何时合并、证据如何引用。增加工人之前，先明确工件所有权和验收门；否则并发只会增加冲突。

本条作为组织框架而非新算法证据；没有统一实验数值。具体权限、沙盒和事务能力仍需核查使用的运行时实现。

03

问题 03

怎样恢复执行？

工作区回滚与外部授权是不同的状态。

超时可能意味着工具未执行，也可能已执行但回执丢失。盲目重试会把同一外部动作执行两次；只保存聊天历史或文件快照不足以判定。

Fork、Restore、Merge还可能丢失任务仍要求的结果。可靠运行时要维护动作身份、授权进度、当前规则与并发调用，检查恢复之后仍然可完成。

读图前的算例 · 教学示意

提交报告成功但回执丢失后，恢复到提交前检查点；先查同一动作ID状态，再复用结果或重试，不重新创造另一个提交动作。

When Can Agents Safely Checkpoint, Fork, Restore, and Merge? Exact Checking for Execution Edits

2026-08-24

恢复不回滚授权；从记录计算所有安全续行。

  1. 论文区分工作区快照、流程调用、动作身份、授权日志和已发请求。Checkpoint只保存当前位置；Fork、Restore和Merge会改变后续工作，但不能撤销此前已经授权或发出的外部动作。
  2. 可信运行时从不可由Agent改写的记录推导编辑后的工作流，检查仍需保留的结果及已授权动作；同一动作的重试复用授权。不是相信模型声称“刚才没成功”，而是查可验证记录。
  3. 接教学例：工具已写入补丁或提交外部结果，回执在中断中丢失。恢复旧提示并重发会重复副作用；正确恢复要先按动作ID查询记录/远端幂等结果。论文明确假设远端幂等或可查询服务提供完成记录。
  4. 有限检查器枚举安全执行集合并不断删除会导致仍需结果无法完成的路径；若为空则返回可检查的拒绝证明。编辑生效前重新检查并原子切换规则，处理工具调用与编辑的竞争。
  5. 这解决的是已注册有限流程及可信边界内的安全性，不能被表述为给任何自由形式Agent自动加上事务保证。

04

问题 04

怎样从失败改进？

执行轨迹驱动候选代码，选择与回退需要证据。

把失败归因到工具接口、控制逻辑或上下文机制，才知道应该改哪里；不能每遇失败就更换所有提示。

无标签环境只能看到代理信号。公开测试通过、候选一致或看起来完整都可能与真实正确性脱节，因此新版本需要回归、留出与回退。

读图前的算例 · 教学示意

从“未复现就改”“空补丁提交”的轨迹中提议两个harness补丁；在同预算样本上运行，查看产物和轨迹再选择。

TTHE: Test-Time Harness Evolution

2026-07-09

固定模型，用无标签执行轨迹改写并选择运行框架。

  1. 优化对象是冻结模型外的可执行harness程序；每个无标签批次从当前框架出发，运行G条候选分支，各自读取轨迹并连续改写R轮，最终judge选择一个提交到下一批。
  2. 执行健康、形状一致、往返检查和公开测试只是代理信号，轨迹与信号一起供proposer/judge使用。隐藏标签只在选择后评分；代码能跑或候选一致都不保证答案正确。
  3. 接教学例：失败轨迹显示“没复现就修”“空补丁也提交”，候选框架可加入先复现、空补丁后重试、修后回归等控制代码。改变的是持续执行策略，不只是当前答案多写一次。
  4. 只在末轮候选中提交意味着较早的好候选可能丢失；G和R的作用非单调。该论文在同批输入上适配后评分，属于transductive结果，不能宣称为未见任务迁移。

05

问题 05

改版比重试强吗？

比较预算、反馈与留出迁移，防止评测过拟合。

新版本多用了几倍推理、验证或任务反馈，本来就可能更好；对照应有同预算并行采样、顺序重试，以及相同工具环境。

可观测性包括调用ID、输入输出、动作关系、耗时、预算、候选版本与最终验收。离线回放检查决策变化，真实复跑检验环境副作用和依赖漂移，二者不互相替代。

读图前的算例 · 教学示意

把改版前后的项目按未见留出任务复跑；查看成功率、总时间和成本，并保留失败样例。只有同任务反复调出的提升不能叫通用技能升级。

Rethinking the Evaluation of Harness Evolution for Agents

2026-07-14

用等预算搜索和留出任务检查真正的可复用改进。

  1. 论文把固定harness下的并行采样、序列修正，与跨任务harness evolution、单任务harness scaling放在同一预算和反馈条件下比较。多做尝试本身就可能提高成绩。
  2. 分别评测无单元测试反馈、有反馈、搜索与评估任务分离三种协议；Terminal-Bench 2.1共89任务，修复原基准的28项依赖/预算/测试不一致，所有方法K=5并平均两次运行。
  3. 接教学例：新框架若在已经看过回归输出的同一任务上更好，只能证明它适应该任务。需要拿未用于改写的项目，以等调用/时间预算和简单多次重试对比，才判断技能版本是否值得发布。
  4. 结果并非否定一切自动演进：终端任务没有一致超过简单搜索，某些长程游戏更有空间。结论应绑定任务、反馈和预算，而不是声称框架演进一定优越或无效。
