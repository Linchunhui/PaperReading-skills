第23章：Agent-to-Agent Communication (A2A)

智能体间通信——从协议设计到多Agent协作的完整技术栈

来源：Agentic AI · 第23章（pp. 417–437） · 阅读笔记

章节摘要

当单个Agent的能力不再足以应对复杂任务时，多Agent协作成为必然选择。本章系统性地解析了Agent-to-Agent（A2A）通信的完整技术体系：从Google提出的A2A开放协议出发，深入探讨通信模式（请求-响应、流式、多轮、广播、发布-订阅、协商、拍卖）、Agent发现与路由机制、消息格式设计、协调协议（合同网、黑板系统、共识、领导者选举）、与MCP的对比定位、安全信任机制，最终通过一个Multi-Agent Research Workflow实例将所有概念落地。本章是构建生产级多Agent系统的通信基础设施蓝图。

23.1 Motivation: Why Agents Must Communicate

单Agent系统面临根本性的能力天花板：一个Agent不可能精通所有领域、拥有所有工具权限、或在合理时间内完成所有子任务。Agent间通信是将"单体智能"升级为"群体智能"的关键基础设施。

单Agent的局限性

  • 知识边界：单个Agent的context window和训练数据无法覆盖所有专业领域（法律、医疗、金融各需专家Agent）
  • 工具碎片化：不同系统的API权限分散，单Agent不可能也不应该持有所有凭证
  • 计算瓶颈：复杂任务需要并行处理——搜索、分析、生成可同时进行
  • 可靠性要求：单点失败风险，多Agent架构天然提供冗余和容错
  • 组织映射：现实组织结构本身就是多Agent协作的——团队、部门、供应链

Multi-Agent系统的价值主张

$$\text{System Capability} = \sum_{i=1}^{N} C_i + \underbrace{\sum_{i \neq j} \text{Synergy}(i, j)}_{\text{协作增益}} - \underbrace{\text{CommOverhead}(N)}_{\text{通信开销}}$$

系统总能力 = 各Agent个体能力之和 + Agent间协作产生的协同效应 - 通信协调带来的开销。A2A协议的设计目标是最大化协同效应、最小化通信开销。

核心洞察：A2A通信不仅仅是"消息传递"——它是一个完整的协作基础设施，包含发现（谁能帮忙？）、协商（如何分工？）、协调（进度如何同步？）、和信任（对方可靠吗？）四个维度。缺少任何一个维度，多Agent系统都无法在生产环境中可靠运行。

从MCP到A2A的演进

如果说MCP（Model Context Protocol）解决了"Agent如何使用工具"的问题，那么A2A解决的是"Agent如何与Agent协作"的问题。二者是互补而非竞争关系：

  • MCP：Agent ↔ Tool（垂直集成，主从关系）
  • A2A：Agent ↔ Agent（水平协作，对等关系）

23.2 The Google A2A Protocol

Google于2025年4月发布的Agent-to-Agent（A2A）协议是首个面向多Agent互操作性的开放标准。其核心设计哲学是：让不同框架、不同厂商构建的Agent能够像Web服务一样互相发现和协作。

Design Philosophy（设计哲学）

  1. Agent-Native：协议原生支持Agent的核心特征——不确定性、长时间运行、多轮交互，而非将Agent硬塞入传统RPC框架
  2. Build on Web Standards：基于HTTP、JSON-RPC 2.0、SSE等成熟Web标准，降低采用门槛
  3. Opaque Execution：Agent是黑盒——调用方无需了解对方的内部实现（用的什么LLM、什么框架）
  4. Capability Discovery：通过Agent Card实现自描述和自动发现，类似Web Service的WSDL/OpenAPI
  5. Secure by Design：内置OAuth 2.0、mTLS等企业级安全机制

Agent Cards（智能体名片）

Agent Card是A2A协议的发现机制核心——每个Agent在 /.well-known/agent.json 路径下暴露一个自描述文件，类似于OpenAPI的Swagger文档。Client Agent通过读取Agent Card即可了解Remote Agent的能力、输入输出格式和认证要求。

{
  "name": "ResearchAgent",
  "description": "Performs deep research on academic topics with citation tracking",
  "url": "https://research-agent.example.com",
  "version": "1.2.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "stateTransitionHistory": true
  },
  "skills": [
    {
      "id": "literature-search",
      "name": "Literature Search",
      "description": "Search and summarize academic papers on a given topic",
      "inputModes": ["text/plain", "application/json"],
      "outputModes": ["text/plain", "application/json", "text/markdown"]
    },
    {
      "id": "citation-analysis",
      "name": "Citation Analysis",
      "description": "Analyze citation networks and identify key papers",
      "inputModes": ["application/json"],
      "outputModes": ["application/json", "image/png"]
    }
  ],
  "authentication": {
    "schemes": ["OAuth2"],
    "credentials": "https://auth.example.com/.well-known/openid-configuration"
  },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["text/plain", "application/json"]
}

Agent Card的设计智慧：与传统API文档不同，Agent Card不暴露具体的函数签名或参数schema——因为Agent的交互是自然语言驱动的。skills 字段描述的是Agent"能做什么"而非"怎么调用"，这体现了A2A"opaque execution"的哲学：调用方只需描述意图，执行方自主决定如何完成。

Task Lifecycle（任务生命周期）

A2A中的核心抽象是Task——一个有状态的工作单元，具有明确的生命周期：

状态含义触发条件
submitted任务已提交，等待处理Client发送 tasks/send
workingAgent正在处理中Agent开始执行
input-requiredAgent需要更多输入信息Agent判断信息不足
completed任务成功完成Agent生成最终结果
failed任务执行失败不可恢复错误
canceled任务被取消Client主动取消 或 超时

Streaming / SSE（流式传输）

对于长时间运行的任务（如深度研究、代码生成），A2A通过 tasks/sendSubscribe 端点支持Server-Sent Events（SSE）流式响应。Client可以实时接收任务状态更新和部分结果：

// Client subscribes to task updates via SSE
POST /a2a/tasks/sendSubscribe
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "method": "tasks/sendSubscribe",
  "id": "req-001",
  "params": {
    "id": "task-abc-123",
    "message": {
      "role": "user",
      "parts": [{"type": "text", "text": "Research quantum computing advances in 2025"}]
    }
  }
}

// SSE Response Stream:
event: status
data: {"taskId": "task-abc-123", "state": "working", "message": "Searching databases..."}

event: artifact
data: {"taskId": "task-abc-123", "artifact": {"name": "interim-results", "parts": [...]}}

event: status
data: {"taskId": "task-abc-123", "state": "completed"}

Push Notifications（推送通知）

当Client无法维持长连接（如移动端、Serverless环境）时，A2A支持Webhook-based推送通知：

  • Client在创建Task时注册一个 pushNotificationUrl
  • Remote Agent在状态变更时向该URL发送POST请求
  • 支持 tasks/pushNotification/set 和 tasks/pushNotification/get 管理通知配置

Message Format（消息格式）

A2A消息由 Message 对象组成，每条消息包含一个或多个 Part：

{
  "role": "agent",  // "user" | "agent"
  "parts": [
    {"type": "text", "text": "Here is the analysis report:"},
    {"type": "file", "file": {"name": "report.pdf", "mimeType": "application/pdf", "uri": "https://..."}},
    {"type": "data", "data": {"citations": 42, "confidence": 0.95}}
  ],
  "metadata": {
    "timestamp": "2025-04-15T10:30:00Z",
    "traceId": "trace-xyz-789"
  }
}

Part类型支持：text（纯文本）、file（文件引用或内联Base64）、data（结构化JSON数据）。这种多模态消息设计允许Agent间传递富内容——不仅是文字，还有文件、图表、结构化数据。

Authentication（认证机制）

A2A协议的安全层基于现有Web标准：

  • OAuth 2.0：标准bearer token认证，支持Client Credentials和Authorization Code流程
  • mTLS：双向TLS证书认证，适用于高安全需求的企业内网场景
  • API Keys：简化场景下的静态密钥认证
  • 认证要求声明在Agent Card的 authentication 字段中，Client在发现阶段即可获知

23.3 Communication Patterns（通信模式）

不同的协作场景需要不同的通信模式。A2A协议的灵活设计支持从简单到复杂的多种模式：

23.3.1 Request-Response（请求-响应）

最简单的同步模式——Client发送请求，等待Agent返回完整结果。适用于延迟敏感、结果确定性高的短任务。

// Synchronous: tasks/send → wait → complete response
Client → tasks/send(message) → Remote Agent
Remote Agent → {status: "completed", artifacts: [...]} → Client

23.3.2 Streaming（流式）

通过SSE实现的异步流式模式。Agent边处理边返回中间结果，适用于长时间运行任务（深度搜索、大文档生成）。Client可实时展示进度。

23.3.3 Multi-Turn（多轮交互）

通过 input-required 状态实现的交互式协作。Agent发现信息不足时暂停并向Client请求澄清，形成多轮对话：

Client → "Analyze this dataset" → Agent
Agent → {state: "input-required", message: "Which metrics do you want?"}
Client → "Focus on accuracy and latency" → Agent
Agent → {state: "completed", artifacts: [analysis_report]}

23.3.4 Broadcast（广播）

一对多通信——Orchestrator Agent同时向多个Worker Agent分发相同任务或通知。适用于并行处理场景（如同时搜索多个数据源）。

23.3.5 Pub-Sub（发布-订阅）

事件驱动的解耦模式——Agent发布事件到Topic，订阅该Topic的其他Agent异步接收。适用于松耦合系统：

  • 新数据到达 → 触发分析Agent
  • 任务完成 → 通知下游依赖Agent
  • 异常检测 → 广播告警到所有监控Agent

23.3.6 Negotiation（协商）

多Agent之间通过多轮消息交换达成共识或最优分工。典型场景：多个Agent竞标同一任务，通过能力声明和成本估算协商由谁执行。

$$\text{Negotiation Outcome} = \arg\max_{a \in \text{Agents}} \frac{\text{Capability}(a, \text{task}) \cdot \text{Availability}(a)}{\text{Cost}(a, \text{task})}$$

协商结果选择能力匹配度高、可用性好、成本低的Agent。实际中可通过多轮消息逐步缩小候选范围，或使用拍卖机制一步达成。

23.3.7 Auction-Based（拍卖模式）

基于经济学拍卖理论的任务分配机制——Orchestrator发布任务需求，各Agent提交竞标（bid），包含预期成本、时间、质量承诺。适用于开放市场场景，如Agent Marketplace。

23.4 Agent Discovery and Routing（发现与路由）

在规模化的多Agent系统中，"找到正确的Agent"本身就是一个非平凡问题。A2A生态需要健壮的发现和路由基础设施。

23.4.1 Registries（注册中心）

类似于DNS之于Web或Service Registry之于微服务，Agent Registry是多Agent系统的发现基础设施：

注册中心类型适用场景实现方式
Static Registry小型/固定Agent集群配置文件列举所有Agent Card URL
DNS-based Discovery互联网级开放生态/.well-known/agent.json 约定路径
Dynamic Registry弹性/云原生环境Agent启动时注册、下线时注销
Federated Registry跨组织协作多注册中心互联、元数据同步

23.4.2 Capability-Based Routing（基于能力的路由）

路由层根据任务需求自动匹配最合适的Agent：

class CapabilityRouter:
    def route(self, task_description: str, required_modalities: list) -> Agent:
        """Route task to best-matching agent based on capabilities."""
        candidates = self.registry.search(
            query=task_description,
            input_modes=required_modalities
        )
        # Score candidates by relevance, load, and past performance
        scored = [
            (agent, self.score(agent, task_description))
            for agent in candidates
        ]
        scored.sort(key=lambda x: x[1], reverse=True)
        return scored[0][0] if scored else self.fallback_agent

路由决策可基于：

  • 语义匹配：将任务描述与Agent Card的skill描述做embedding相似度计算
  • 模态匹配：确保Agent支持所需的输入/输出格式
  • 历史绩效：基于过往成功率、延迟、质量评分加权
  • 当前负载：避免将任务路由到已饱和的Agent

23.4.3 Load Balancing（负载均衡）

当多个Agent具备相同能力时，需要负载均衡策略：

  • Round-Robin：轮询分配，最简单
  • Least-Connections：分配给当前活跃任务最少的Agent
  • Weighted：根据Agent性能等级加权分配
  • Locality-Aware：优先路由到网络距离最近的Agent实例（减少延迟）

23.4.4 Version Management（版本管理）

Agent Card中的 version 字段支持语义化版本控制。路由层可实现：

  • Canary Routing：新版本Agent只接收小比例流量，逐步放量
  • Backward Compatibility：Client可指定最低版本要求
  • Graceful Deprecation：旧版Agent返回deprecation warning，引导迁移

23.5 Message Formats（消息格式设计）

23.5.1 Structured vs. Unstructured（结构化 vs. 非结构化）

A2A消息设计的核心张力在于：Agent之间的通信既需要机器可解析的结构化数据（用于自动化处理），又需要自然语言的灵活性（用于表达复杂意图）。A2A通过 parts 数组的多态设计同时支持两者：

消息类型适用场景优势劣势
纯文本 (text)意图表达、解释性通信灵活、无schema约束解析不确定性
结构化数据 (data)精确参数传递、结果返回机器友好、可验证表达力受限
文件引用 (file)大型数据、二进制内容不占消息体积需额外网络请求
混合消息实际生产场景兼具两者优势解析复杂度增加

23.5.2 Multi-Modal Messages（多模态消息）

现代Agent不仅处理文本——视觉Agent需要接收图片，音频Agent需要接收语音。A2A的file part支持任意MIME类型：

  • image/png, image/jpeg：视觉内容
  • application/pdf：文档
  • audio/wav, audio/mp3：音频
  • video/mp4：视频
  • 文件可通过URI引用（大文件）或Base64内联（小文件 < 10MB）

23.5.3 Context Passing（上下文传递）

多Agent协作的关键挑战之一是上下文如何在Agent链中传递而不丢失关键信息：

$$\text{Context Loss}(n) = 1 - \prod_{i=1}^{n} (1 - \epsilon_i)$$

经过 $n$ 个Agent的链式传递后，上下文信息损失率。$\epsilon_i$ 是第 $i$ 个Agent的信息丢失率。即使每步只丢失5%，经过10个Agent后总损失率已达 $1 - 0.95^{10} \approx 40\%$。这说明了Context Passing机制的重要性。

A2A的解决方案：

  • Task History：完整的消息历史随Task对象传递，Agent可查看前序交互
  • Artifacts：中间结果以Artifact形式持久化，后续Agent可引用
  • Metadata Propagation：traceId、sessionId等元数据自动透传，支持全链路追踪

23.5.4 Conversation Threading（对话线程）

复杂协作中，单个Task可能产生多个并行子对话。Threading机制通过 taskId + contextId 维护对话树结构，防止信息混乱。

23.6 Coordination Protocols（协调协议）

当多个Agent需要协同完成复杂任务时，需要正式的协调协议来确保一致性和效率。以下是四种经典协调模式：

23.6.1 Contract Net Protocol（合同网协议）

源自Smith（1980）的经典多Agent协调机制，模拟现实世界的招标-投标过程：

  1. Task Announcement：Manager Agent向所有潜在Contractor Agent广播任务需求
  2. Bidding：感兴趣且有能力的Agent提交投标（包含预计时间、成本、质量承诺）
  3. Award：Manager评估所有bid，选择最优Contractor并授予合同
  4. Execution：获选Agent执行任务并报告结果
class ContractNetManager:
    async def delegate_task(self, task: Task) -> Result:
        # 1. Announce task to potential contractors
        announcements = await self.broadcast(
            task_spec=task.to_spec(),
            deadline=timedelta(seconds=30)
        )
        
        # 2. Collect bids
        bids = await self.collect_bids(timeout=30)
        
        # 3. Evaluate and award
        best_bid = max(bids, key=lambda b: self.evaluate_bid(b, task))
        contract = await self.award_contract(best_bid.agent, task)
        
        # 4. Monitor execution
        result = await contract.await_completion(timeout=task.deadline)
        return result
    
    def evaluate_bid(self, bid: Bid, task: Task) -> float:
        """Multi-criteria bid evaluation."""
        return (
            0.4 * bid.capability_match +
            0.3 * bid.speed_score +
            0.2 * (1 - bid.cost_normalized) +
            0.1 * bid.reputation
        )

23.6.2 Blackboard System（黑板系统）

共享工作空间模式——所有Agent读写同一个"黑板"（共享状态空间），各自贡献部分解决方案：

  • Blackboard：共享数据结构，存储问题状态和部分解
  • Knowledge Sources：各专家Agent，监控黑板变化并贡献知识
  • Controller：调度器，决定下一步由哪个Agent行动

适用场景：黑板系统特别适合"没有预定义工作流"的开放式问题——如诊断、设计、研究。每个Agent观察当前状态，在自己能贡献时自主行动，系统逐步收敛到解。

23.6.3 Consensus Protocols（共识协议）

当多个Agent必须就某个决策达成一致时（如多数投票验证、集体决策），需要分布式共识算法：

$$\text{Consensus}(v_1, v_2, \ldots, v_n) \to v^* \quad \text{s.t.} \quad |\{i : v_i = v^*\}| \geq \lceil \frac{n+1}{2} \rceil$$

$n$ 个Agent分别给出判断 $v_i$，共识结果 $v^*$ 须获得超过半数Agent的支持。在Agent系统中，这常用于多Agent投票验证（如代码审查、事实核查）。

实践方案包括：

  • Majority Voting：简单多数投票，适用于分类/判断型任务
  • Weighted Voting：根据Agent在该领域的专业度加权
  • Debate + Judge：多Agent辩论后由Judge Agent仲裁
  • Iterative Refinement：轮流修改方案直到所有Agent接受

23.6.4 Leader Election（领导者选举）

动态多Agent系统中，需要选出协调者来分配任务和解决冲突。Leader Election算法确保即使原Leader下线，系统也能快速选出新Leader：

  • Bully Algorithm：ID最大的Agent成为Leader，简单但不健壮
  • Raft-inspired：心跳检测 + 投票选举，容忍少数节点故障
  • Capability-based：根据当前任务需求动态选出最合适的Leader（非固定角色）

23.7 A2A vs. MCP（对比分析）

A2A和MCP是多Agent生态中的两大互补协议。理解它们的边界和协同方式是正确架构设计的前提。

When to Use Which（何时使用哪个）

维度MCP (Model Context Protocol)A2A (Agent-to-Agent)
关系模型主从关系（Client ↔ Server）对等关系（Agent ↔ Agent）
核心抽象工具调用（Tool Call）任务委托（Task Delegation）
交互模式同步、确定性、短生命周期异步、非确定性、长生命周期
对方性质确定性服务/工具自主Agent（有自己的目标和推理）
发现机制工具Schema描述Agent Card自描述
状态模型无状态（单次调用）有状态（Task生命周期）
结果确定性确定性（相同输入→相同输出）非确定性（Agent有自主性）
通信格式Schema-defined（JSON Schema）Opaque（自然语言+结构化）
典型场景数据库查询、文件操作、API调用研究协作、多专家分析、流程协调
类比使用一把螺丝刀委托同事完成子项目

判断准则：如果你需要的是"执行一个确定性操作并返回结果"→ 用MCP；如果你需要的是"委托一个有自主推理能力的实体去解决一个开放性问题"→ 用A2A。关键区别在于：MCP的Server没有自己的"想法"，A2A的Remote Agent有。

在这个组合架构中：

  • 上层（A2A）：Agent间使用A2A协议进行任务委托和协作——Orchestrator将研究任务委托给Research Agent，将数据分析委托给Analysis Agent
  • 下层（MCP）：每个Agent内部使用MCP连接具体工具——Research Agent通过MCP调用Search API和Database，Writing Agent通过MCP操作File System
  • 设计原则：A2A处理"智能体间协作"，MCP处理"智能体与工具的连接"。二者的分层清晰、职责明确。

23.8 Security and Trust（安全与信任）

多Agent系统的安全挑战远超单Agent场景——每个Agent都是潜在的攻击面，Agent间的通信可能被窃听或篡改，恶意Agent可能冒充合法Agent。

23.8.1 Identity Verification（身份验证）

  • Agent Identity：每个Agent持有唯一标识（DID或X.509证书），在通信前验证对方身份
  • Mutual Authentication：双方互相验证，防止中间人攻击
  • Identity Federation：跨组织场景下，通过IdP（Identity Provider）实现统一身份管理

23.8.2 Message Integrity（消息完整性）

  • Digital Signatures：每条消息附带发送方的数字签名，接收方可验证消息未被篡改
  • Content Hashing：对Artifact内容计算哈希，确保传输过程中数据完整
  • Replay Protection：通过nonce和timestamp防止消息重放攻击
$$\text{Signature} = \text{Sign}(SK_{\text{sender}}, H(\text{message} \| \text{nonce} \| \text{timestamp}))$$

发送方用私钥 $SK_{\text{sender}}$ 对消息内容、随机数、时间戳的联合哈希进行签名。接收方用发送方公钥验证，确保消息来源可信且未被篡改。

23.8.3 Authorization Scopes（授权范围）

不同Agent拥有不同权限级别，遵循最小权限原则：

{
  "agent": "research-agent-001",
  "scopes": [
    "task:read",
    "task:create",
    "artifact:read",
    "artifact:write:text/*",
    "notification:subscribe"
  ],
  "restrictions": {
    "maxConcurrentTasks": 10,
    "allowedDataClassifications": ["public", "internal"],
    "deniedOperations": ["task:cancel:others", "admin:*"]
  },
  "expiry": "2025-12-31T23:59:59Z"
}

23.8.4 Audit Trails（审计追踪）

生产级多Agent系统需要完整的审计日志：

  • Who：哪个Agent发起/执行了操作
  • What：具体的消息内容和操作类型
  • When：精确时间戳（全链路统一时钟）
  • Why：决策的推理链路（通过traceId串联）
  • Outcome：操作结果和影响范围

信任等级模型：实践中可建立Agent信任分层——从"完全信任"（内部Agent，同一安全域）到"有限信任"（合作伙伴Agent，通过联邦认证）再到"零信任"（外部Agent，每次交互都需完整验证）。信任等级决定了认证强度、授权范围和审计粒度。

23.9 Implementation Example: Multi-Agent Research Workflow

以下是一个完整的Multi-Agent Research Workflow实现，展示A2A协议在实际场景中的应用——用户提出研究问题，多个专家Agent协作完成文献搜索、分析和报告生成。

import asyncio
from dataclasses import dataclass
from typing import List, Optional
import httpx

@dataclass
class A2AMessage:
    role: str  # "user" | "agent"
    parts: List[dict]
    metadata: Optional[dict] = None

@dataclass
class TaskResult:
    task_id: str
    state: str
    artifacts: List[dict]

class A2AClient:
    """Client for communicating with remote agents via A2A protocol."""
    
    def __init__(self, agent_url: str, auth_token: str):
        self.agent_url = agent_url
        self.auth_token = auth_token
        self.client = httpx.AsyncClient(
            headers={"Authorization": f"Bearer {auth_token}"}
        )
    
    async def discover(self) -> dict:
        """Fetch remote agent's Agent Card."""
        resp = await self.client.get(f"{self.agent_url}/.well-known/agent.json")
        return resp.json()
    
    async def send_task(self, task_id: str, message: A2AMessage) -> TaskResult:
        """Send a task via A2A tasks/send endpoint."""
        payload = {
            "jsonrpc": "2.0",
            "method": "tasks/send",
            "id": f"req-{task_id}",
            "params": {
                "id": task_id,
                "message": {
                    "role": message.role,
                    "parts": message.parts
                }
            }
        }
        resp = await self.client.post(f"{self.agent_url}/a2a", json=payload)
        result = resp.json()["result"]
        return TaskResult(
            task_id=result["id"],
            state=result["status"]["state"],
            artifacts=result.get("artifacts", [])
        )
    
    async def subscribe_task(self, task_id: str, message: A2AMessage):
        """Stream task updates via SSE (tasks/sendSubscribe)."""
        payload = {
            "jsonrpc": "2.0",
            "method": "tasks/sendSubscribe",
            "id": f"req-{task_id}",
            "params": {"id": task_id, "message": {"role": message.role, "parts": message.parts}}
        }
        async with self.client.stream("POST", f"{self.agent_url}/a2a", json=payload) as resp:
            async for line in resp.aiter_lines():
                if line.startswith("data:"):
                    yield json.loads(line[5:])


class ResearchOrchestrator:
    """Orchestrator that coordinates multiple agents for research tasks."""
    
    def __init__(self):
        self.search_agent = A2AClient("https://search-agent.example.com", token)
        self.analysis_agent = A2AClient("https://analysis-agent.example.com", token)
        self.writer_agent = A2AClient("https://writer-agent.example.com", token)
        self.qa_agent = A2AClient("https://qa-agent.example.com", token)
    
    async def execute_research(self, query: str) -> dict:
        """Execute full research workflow using A2A communication."""
        
        # Phase 1: Parallel search across multiple sources
        search_msg = A2AMessage(role="user", parts=[
            {"type": "text", "text": f"Find relevant papers on: {query}"},
            {"type": "data", "data": {"maxResults": 20, "recency": "2024-2025"}}
        ])
        search_result = await self.search_agent.send_task("search-001", search_msg)
        
        # Phase 2: Deep analysis of search results
        analysis_msg = A2AMessage(role="user", parts=[
            {"type": "text", "text": "Analyze these papers and identify key findings"},
            {"type": "data", "data": {"papers": search_result.artifacts}}
        ])
        analysis_result = await self.analysis_agent.send_task("analysis-001", analysis_msg)
        
        # Phase 3: Generate research report
        write_msg = A2AMessage(role="user", parts=[
            {"type": "text", "text": "Write a comprehensive research report"},
            {"type": "data", "data": {"analysis": analysis_result.artifacts}}
        ])
        draft = await self.writer_agent.send_task("write-001", write_msg)
        
        # Phase 4: Fact-check and quality assurance
        qa_msg = A2AMessage(role="user", parts=[
            {"type": "text", "text": "Verify all claims and citations in this report"},
            {"type": "data", "data": {"report": draft.artifacts, "sources": search_result.artifacts}}
        ])
        final = await self.qa_agent.send_task("qa-001", qa_msg)
        
        return {"status": "completed", "report": final.artifacts}


# Usage
async def main():
    orchestrator = ResearchOrchestrator()
    result = await orchestrator.execute_research(
        "Recent advances in Agent-to-Agent communication protocols"
    )
    print(f"Research complete: {len(result['report'])} artifacts generated")

实现要点总结：

  • Orchestrator通过A2A协议与各专家Agent通信，不关心它们的内部实现
  • 消息使用 parts 数组混合自然语言意图和结构化数据
  • 任务通过 task_id 追踪，支持异步和流式
  • 工作流可扩展：增加新Agent只需注册新的Agent Card
  • 错误处理：每个阶段可独立重试，不影响整体流程

23.10 Summary

核心要点回顾

  1. A2A是多Agent协作的通信标准：解决Agent间的发现、通信、协调和信任问题，补充MCP的Agent-to-Tool能力
  2. Agent Card是发现基础：通过 /.well-known/agent.json 实现自描述和自动发现，类似API世界的OpenAPI
  3. Task是核心抽象：具有完整生命周期（submitted→working→completed），支持长时间运行和多轮交互
  4. 通信模式丰富多样：从简单请求-响应到复杂的协商和拍卖，适配不同协作场景
  5. 协调协议保障一致性：Contract Net、Blackboard、Consensus、Leader Election各有适用场景
  6. A2A + MCP分层互补：A2A处理Agent间协作（水平），MCP处理Agent-Tool连接（垂直）
  7. 安全必须内建而非外挂：身份验证、消息完整性、授权范围、审计追踪缺一不可
  8. 基于Web标准降低门槛：HTTP + JSON-RPC + SSE + OAuth 2.0，无需学习新传输协议

复习与思考 Q&A

Q1：A2A协议中Agent Card的作用是什么？它与OpenAPI Spec有何异同？

作用：Agent Card是A2A的发现机制，允许Client Agent在调用前了解Remote Agent的能力、支持的输入/输出模态、认证要求等。它托管在 /.well-known/agent.json。

与OpenAPI的相似处：都是自描述文档、都支持自动发现、都声明了"对方能做什么"。

关键区别：OpenAPI描述精确的函数签名和参数Schema（确定性调用），而Agent Card只描述"能力"和"技能"——不暴露内部实现细节。因为Agent的交互是自然语言驱动的，调用方描述意图而非构造精确参数。这体现了A2A"opaque execution"的设计哲学。

Q2：A2A的Task生命周期中，input-required状态解决了什么问题？

input-required 解决了Agent无法一次性获取所有必要信息的问题。传统RPC要求调用时提供完整参数，但Agent任务往往是开放性的——Agent在执行过程中才发现需要更多上下文。例如研究Agent被要求"分析市场趋势"，执行中发现需要确认"哪个市场？""什么时间范围？"。通过 input-required 状态，Agent可以暂停执行、向Client请求澄清，然后继续——形成人机/Agent间的多轮协作循环。这也是A2A"Agent-Native"设计哲学的体现：承认不确定性是Agent交互的常态。

Q3：为什么A2A和MCP不是竞争关系而是互补关系？请用具体例子说明。

二者解决不同层次的问题：MCP = "Agent如何使用工具"，A2A = "Agent如何与Agent协作"。

例子：考虑一个"帮我分析竞品定价策略"的任务。Orchestrator Agent通过A2A将"数据收集"委托给Data Agent、将"价格建模"委托给Analytics Agent。而Data Agent内部通过MCP调用Web Scraper工具抓取网页、调用Database工具存储数据；Analytics Agent通过MCP调用Python REPL跑回归模型。

A2A处理的是"谁做什么"（任务分配），MCP处理的是"怎么做"（工具调用）。前者涉及自主推理和协商，后者是确定性执行。

Q4：Contract Net Protocol的四步流程是什么？它比简单的Round-Robin分配有什么优势？

四步流程：(1) Task Announcement——Manager广播任务需求；(2) Bidding——感兴趣的Agent提交投标；(3) Award——Manager评估并选择最佳Contractor；(4) Execution——获选Agent执行并报告结果。

优势：Contract Net是"信息驱动"的分配——每个Agent根据自己当前的能力、负载和成本自主决定是否投标以及报价多少。这自然实现了负载均衡（忙的Agent不会投标）、能力匹配（不具备能力的Agent不会投标）和动态适应（新Agent上线自动参与）。Round-Robin则是"无信息"的——它不考虑Agent的当前状态和能力匹配度。

Q5：多Agent系统中的上下文传递为什么会导致信息损失？如何缓解？

信息损失原因：每当一个Agent将上下文传递给下一个Agent时，都可能发生压缩、摘要或遗漏（Agent的context window有限，不可能传递完整历史）。经 $n$ 步传递后，损失率为 $1 - \prod(1-\epsilon_i)$，随链路长度指数增长。

缓解策略：(1) Artifact持久化——将关键中间结果作为Artifact保存，后续Agent直接引用原始数据而非前Agent的摘要；(2) Metadata透传——traceId等元数据自动传播，可回溯完整历史；(3) Shared Workspace——采用Blackboard模式，所有Agent读写同一状态空间，避免链式传递；(4) Context Window最大化——尽量将原始数据而非转述传递给下游Agent。

Q6：在设计多Agent安全架构时，"零信任"模型意味着什么？

零信任意味着每次Agent间交互都需要完整验证，不因"上次验证过"或"在同一网络内"而放松安全要求。具体包括：(1) 每条消息都附带数字签名和时间戳（防篡改+防重放）；(2) 每次请求都要验证对方身份和授权范围（不缓存信任）；(3) 最小权限原则——Agent只获得完成当前任务所需的最小权限集；(4) 完整审计——所有交互被记录用于事后审查。

实践中，可以对内部Agent（同一安全域）使用"信任但验证"，对外部Agent严格零信任，通过信任等级模型平衡安全性与性能。

Q7：Streaming模式（SSE）相比简单的轮询（Polling）有什么优势？什么场景下应选择Push Notifications？

SSE vs Polling：SSE是服务器主动推送，Client无需反复请求——延迟低（实时）、带宽省（无空轮询）、实现简洁（原生HTTP）。Polling则需要Client定期发请求查状态，浪费带宽且有延迟窗口。

选择Push Notifications的场景：(1) Client无法维持长连接（Serverless/Lambda环境）；(2) 移动端需要省电（不能持续连接）；(3) 任务可能运行数小时甚至数天；(4) 多个Client需要订阅同一Task的更新。Push Notifications通过Webhook回调实现——Task状态变更时POST到预注册URL。

Q8：Blackboard系统与Contract Net各自适用什么类型的问题？

Blackboard适用于：开放式、探索性问题——问题解决没有预定义流程，需要多个专家Agent从不同角度贡献知识，系统逐步收敛。例如：医疗诊断（不同科室的Agent各自分析症状）、创意设计（多个设计Agent贡献创意并互相启发）。

Contract Net适用于：可分解的、有明确产出要求的任务——Manager清楚需要什么结果，但不确定谁最适合执行。例如：代码任务分配（多个开发Agent竞标）、数据处理管道（将子任务分配给负载最低的Agent）。

本质区别：Blackboard是"共享状态驱动"（Agent自主决定何时贡献），Contract Net是"Manager驱动"（显式的分配-执行流程）。
