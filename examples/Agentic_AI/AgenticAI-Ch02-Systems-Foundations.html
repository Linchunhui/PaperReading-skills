摘要

本章回答一个核心问题：大模型的训练和推理为什么如此依赖 GPU，怎样才能把 GPU 利用率拉满？

第一部分（2.1）以 NVIDIA GPU 为主线，从"CPU vs GPU 设计哲学"出发，逐步展开微架构代际演进、SM（流式多处理器）内部结构、内存层次（从寄存器到 HBM）、算术强度与 Roofline 模型、Tensor Core 工作原理，以及 NVLink/InfiniBand 通信架构——让读者能判断"这个操作是 memory-bound 还是 compute-bound"。

第二部分（2.2）聚焦 vLLM 推理引擎，介绍 KV Cache 碎片问题、PagedAttention（借鉴 OS 虚拟内存分页）、Continuous Batching、Speculative Decoding、Prefix Caching 和 Guided Decoding，展示如何将 GPU 显存利用率从 20–40% 提升至 90–95%。

2.1 GPU 架构——从硅片到 LLM 训练

2.1.1 为什么深度学习要用 GPU？

CPU 的设计哲学是优化延迟（latency）：大面积芯片预算分配给庞大的缓存层次（L1/L2/L3 可达 64 MB+）、复杂的分支预测器和乱序执行引擎，让少量线程以最低延迟跑完任务。现代服务器 CPU 拥有 8–128 个核心，每核心支持深度流水线和超标量执行。

GPU 的设计哲学完全不同——优化吞吐（throughput）：用海量并行线程（数万到数十万）来隐藏延迟。GPU 的核心面积主要分配给成百上千的计算单元和大容量寄存器堆，而非复杂控制逻辑。线程以 Warp（32 线程）为最小调度单位，数千个 warp 在飞行中交替执行，使数据从 HBM 读取的数百 cycle 延迟被其他 warp 的计算所掩盖。

为什么深度学习天然适合 GPU？ 深度学习的核心运算是矩阵乘法，计算复杂度为 $O(n^3)$，数据规模为 $O(n^2)$——计算/数据比随规模增长而增大，天然适合大规模并行。一个 70B 模型的单次前向传播，每个 token 需要约 140 TFLOP 计算量；反向传播约为前向的 2 倍。这些运算几乎不存在控制流分支，完美匹配 GPU 的 SIMT（Single Instruction, Multiple Threads）执行模型。

2.1.4 GPU 内部架构——流式多处理器 (SM)

整个 GPU 芯片本质上是一个 SM 阵列。每个 SM 像一台微型并行处理器，拥有独立的执行单元、寄存器堆和共享内存。理解 SM 的结构就是理解 GPU 的性能来源。

SM 关键组件（以 A100 为例）：
  • 64 CUDA Cores (FP32)：标量算术单元，负责通用浮点和整数运算
  • 4 Tensor Cores (3rd Gen)：矩阵乘累加专用单元，每周期执行 4×4×4 MMA
  • 4 Warp Schedulers：每 cycle 可各自 dispatch 一条指令，即 SM 内最多 4 个 warp 同时执行
  • Register File (256 KB)：线程私有寄存器，延迟 1 cycle，带宽 >100 TB/s（全芯片合计 ~27 MB）
  • Shared Memory / L1 (192 KB)：可编程片上缓存，用户控制数据放置，延迟 ~20 cycle

A100 全芯片规格：108 个 SM × 64 CUDA Cores = 6,912 FP32 Cores；108 × 4 = 432 Tensor Cores；L2 Cache 40 MB；HBM2e 80 GB @ 2 TB/s。

2.1.7 算术强度与 Roofline 模型

算术强度（Arithmetic Intensity）是判断一个 kernel 瓶颈的第一工具：

$$I = \frac{\text{FLOPs (浮点运算次数)}}{\text{Bytes accessed from HBM (HBM 搬运字节)}}$$

$I$ 越大表示越"计算密集"（compute-bound），越小表示越"带宽受限"（memory-bound）。

Roofline 模型将可达性能表示为：

$$\text{Attainable FLOP/s} = \min\bigl(\text{Peak FLOP/s},\; I \times \text{Peak Bandwidth}\bigr)$$

当 $I < I_{\text{ridge}}$ 时受带宽限制（性能随 $I$ 线性增长）；当 $I \geq I_{\text{ridge}}$ 时受计算限制（性能打到峰值平台）。

屋脊点（Ridge Point）是两条线的交叉点：

$$I_{\text{ridge}} = \frac{\text{Peak FLOP/s}}{\text{Peak Bandwidth}} = \frac{312 \times 10^{12}}{2 \times 10^{12}} = 156 \text{ FLOP/Byte (A100 BF16)}$$

低于 156 的 kernel 是 memory-bound；高于 156 的是 compute-bound。对于 H100：$I_{\text{ridge}} = 989/3.35 \approx 295$ FLOP/Byte。

2.1.8 Attention 是 Memory-Bound；FFN 是 Compute-Bound

标准 Attention 的算术强度分析（设 $n=4096$，$d=128$）：

  • 计算量：$QK^T$ 需 $2n^{2}d$ FLOPs，$\text{Softmax}(S) \cdot V$ 需 $2n^{2}d$ FLOPs → 总计 $4n^{2}d \approx 8.6 \times 10^{9}$ FLOPs
  • HBM 数据搬运（标准实现需写回 $n \times n$ 注意力矩阵 $S$）：Q/K/V 读入 + $S$ 写出 + $S$ 读入 + O 写出 $\approx 138$ MB
  • 算术强度：$I = 8.6 \times 10^{9} / (138 \times 10^{6}) \approx 62$ FLOP/Byte

$62 < 156$（屋脊点），标准 Attention 严重 memory-bound——GPU 约 60% 的时间在等数据搬运。

Flash Attention 如何逆转？ Flash Attention 永远不把 $n \times n$ 矩阵写入 HBM，而是在 SRAM 内做 tiling：

$$I_{\text{Flash}} = \frac{4n^{2}d}{4 \cdot n \cdot d \cdot \text{bytes\_per\_elem}} = \frac{4n^{2}d}{4nd \cdot 2} = \frac{n}{2} = \frac{4096}{2} = 2048 \text{ FLOP/Byte}$$

2048 是屋脊点 156 的 13 倍——从 memory-bound 直接变为深度 compute-bound，GPU 满载运行。

FFN/MLP 层的算术强度（设隐藏维度 $h=8192$，中间维度 $4h=32768$，batch tokens $B=2048$）：

  • 计算量：两个线性层 $2 \times 2 \times B \times h \times 4h = 2 \times 2 \times 2048 \times 8192 \times 32768 \approx 2.2 \times 10^{12}$ FLOPs
  • HBM 搬运：权重 $2 \times h \times 4h \times 2 = 1$ GB + 激活值 ~34 MB ≈ 1.03 GB
  • 算术强度：$I = 2.2 \times 10^{12} / (1.03 \times 10^{9}) \approx 2136$ FLOP/Byte
结论：Attention 层 memory-bound → Flash Attention（减少 HBM 流量）是最有效优化；FFN/MLP 层 compute-bound → 量化（减小权重体积从而减小 GEMM 尺寸）和 Tensor Core 混合精度更有效。

2.1.9 Tensor Cores

Tensor Core 是 NVIDIA 在 Volta (2017) 引入的专用矩阵乘累加（MMA）单元。每个 Tensor Core 在单个时钟周期内完成：

$$D_{4 \times 4} = A_{4 \times 4} \times B_{4 \times 4} + C_{4 \times 4}$$

单个 MMA 操作：$4 \times 4 \times 4 = 64$ FMA（128 FLOPs）。A100 全芯片 432 Tensor Cores × 1.41 GHz ≈ 312 TFLOP/s (BF16)。

各代 Tensor Core 精度支持与吞吐：

代际GPU支持精度峰值 TFLOPSMMA tile
1st GenV100FP161254×4×4
3rd GenA100FP16/BF16/TF32/FP64/INT8312 (BF16)8×8×4 (BF16)
4th GenH100+FP8989 (FP8)WGMMA 64×256×16
5th GenB200+FP44,500 (FP4)更大 tile

使用 Tensor Core 的条件：

  • 矩阵维度必须为 8 (BF16) 或 16 (FP8) 的倍数——不满足时需要 padding
  • 内部以 FP32 累加：低精度输入乘法 → FP32 累加 → 可选舍入回低精度，避免点积中的精度灾难
  • GEMM 必须是 compute-bound：batch=1 推理时 M=1 维度导致 tile 大量空位，Tensor Core 利用率极低
Tensor Core 陷阱：如果 kernel 是 memory-bound（如 batch=1 推理），即使 Tensor Core 计算速度无限快也没用——瓶颈在等数据。这就是推理引擎必须拼命凑大 batch 的根本原因。

NVSwitch：DGX H100 中 8 卡通过 4 个 NVSwitch 实现 full-bisection bandwidth 全互联，任意两卡同时满速通信。相比简单环形拓扑效率提升约 30%。

InfiniBand——跨节点通信：

  • NDR 400 Gb/s = 50 GB/s 单向/端口；多端口可叠加至 400 GB/s/节点
  • GPUDirect RDMA：数据走 HBM → NIC → 网络 → NIC → HBM，完全绕过 CPU，延迟 ~1–2 μs（TCP/IP 约 100 μs）
  • SHARP (In-Network Reduction)：交换机内完成 AllReduce 的 reduce 操作，减半跨节点流量

并行策略与通信拓扑的对应关系：

  • Tensor Parallelism (TP)：每层都做 AllReduce → 通信量大、频率极高 → 只在 NVLink 节点内（TP=8 标准配置）
  • Pipeline Parallelism (PP)：层间 Point-to-Point 通信 → 可跨节点，但有 micro-batch bubble 开销
  • Data Parallelism (DP/FSDP/ZeRO)：梯度 AllReduce 或 AllGather+ReduceScatter → 频率低（每步一次），可走 InfiniBand

实际计算示例——70B 模型梯度 AllReduce 耗时：

设 70B 参数，BF16 梯度，8 节点 × 8 卡 = 64 GPU（数据并行度 64）：

$$\begin{aligned} \text{梯度大小} &= 70 \times 10^{9} \times 2 = 140 \text{ GB} \\ \text{Ring AllReduce 每卡通信量} &= 2 \times \frac{N-1}{N} \times 140 \approx 275 \text{ GB} \\ \text{可用跨节点带宽 (8 NIC)} &= 8 \times 50 = 400 \text{ GB/s} \\ \text{AllReduce 时间} &= 275 / 400 \approx 0.69 \text{ s} \end{aligned}$$

若计算步耗时 1s，通信占比 41%。这就是梯度压缩、通信/计算重叠（FSDP prefetch）、以及 SHARP 在网络内规约等优化的动力来源。

2.2 vLLM——PagedAttention 与高吞吐推理

vLLM (Kwon et al., 2023) 的核心洞察：将操作系统的分页虚拟内存思想引入 GPU KV Cache 管理。在 LLM 推理中，KV Cache 是最大的内存消费者，高效管理它直接决定吞吐量和并发能力。

2.2.1 KV Cache 碎片问题

KV Cache 大小公式：

$$\text{KV Cache (bytes)} = 2 \times L \times H_{\text{kv}} \times d \times n \times b$$

$L$ = 层数，$H_{\text{kv}}$ = KV 头数（GQA 下可能 < $H_q$），$d$ = 头维度，$n$ = 序列长度，$b$ = bytes/element。

以 Llama-3 70B (BF16, GQA $H_{\text{kv}}=8$, $L=80$, $d=128$) 为例：

$$\text{KV per token} = 2 \times 80 \times 8 \times 128 \times 2 = 327{,}680 \text{ bytes} \approx 320 \text{ KB/token}$$

当 $n=4096$ 时，单条序列 KV Cache ≈ 1.28 GB。8×A100-80GB 集群，除去模型权重后可用于 KV 的空间有限。

两种碎片类型：

  • 内部碎片（Internal Fragmentation）：预分配 max_seq_len 块（如 4096 tokens），实际序列可能只用 500 tokens → 87% 空间白白浪费
  • 外部碎片（External Fragmentation）：序列结束释放后，空闲内存散落成大小不一的碎片，新的长序列无法分配，即使总空余充足
实测数据：朴素连续分配策略下，GPU 显存有效利用率通常仅 20–40%，大量显存被碎片"锁死"。

2.2.2 PagedAttention——KV Cache 的虚拟内存

PagedAttention 将 KV Cache 切成固定大小的物理块（Block）（默认每块存 16 tokens 的 KV），并用块表（Block Table）做间接映射——类似 CPU 页表将虚拟地址翻译为物理地址。

核心机制：

  • 逻辑块：每个序列看到连续的逻辑地址空间 [Block 0, Block 1, ...]
  • 物理块池：GPU HBM 预分配好的等大小 block 池，启动时一次性分配，运行时零动态 malloc
  • 块表：每个序列一张，记录 逻辑块号 → 物理块号 的映射
  • 动态分配：序列增长时按需从池中取空闲 block，不需预知最终长度
  • Copy-on-Write (CoW)：共享前缀的多个序列指向同一物理 block；只有某序列写入不同 token 时才拷贝新 block
碎片消除效果：内部碎片最多浪费 1 个 block（最后块未满）；外部碎片彻底消除（所有 block 等大可互换）。显存利用率从 20–40% 跃升至 90–95%。

2.2.3 PagedAttention 的收益量化

以 Llama-3 70B、128 个并发聊天用户、1000-token 共享系统提示为例：

  • 无 PagedAttention + 无前缀共享：每用户独立分配 max_len KV → $128 \times 4096 \times 320\text{KB} \approx 160$ GB KV 需求（超出单节点 8×80GB）
  • PagedAttention（按实际长度分配）：假设平均实际长度 1500 tokens → $128 \times 1500 \times 320\text{KB} \approx 60$ GB
  • + Prefix Sharing：1000-token 系统提示只存一份 → 再节省 $127 \times 1000 \times 320\text{KB} \approx 38.8$ GB

2.2.4 Continuous Batching（连续批处理）

传统 Static Batching 的问题：组成一个 batch 后，必须等 batch 内所有序列都生成完毕才能换新序列——短序列跑完后 GPU 空等长序列，利用率骤降。

Continuous Batching 原理：以单步解码（iteration-level）为调度粒度。每执行完一步：
  1. 检查哪些序列已生成 EOS → 移除，释放其 KV blocks 回池
  2. 从 Waiting Queue 取新请求填充空位（即时分配 KV blocks）
  3. 以更新后的异构 batch 执行下一步前向
Batch 组成每步都在变化——GPU 利用率接近 100%，吞吐提升 1.5–3×。

为什么依赖 PagedAttention？ 动态增删序列需要即时分配/释放 KV 内存。连续分配会产生碎片导致加入新序列失败；分页管理下 block 回池即刻可复用，$O(1)$ 操作。

2.2.5 Speculative Decoding（投机解码）

自回归解码的延迟瓶颈：每步只产生 1 个 token，但要读取全部模型权重。投机解码的思路：

  1. 用一个小的 Draft 模型（如 1B 参数）快速自回归生成 $k$ 个候选 token（$k$ 通常 3–8）
  2. 将 $k$ 个候选一次性喂入大的 Target 模型做并行验证（单次前向 pass，$k+1$ 个位置同时算 logits）
  3. 从左到右逐 token 用 rejection sampling 验证：第一个被拒绝的 token 之前全部接受
  4. 期望每轮接受 3–5 个 token → 等效延迟降低 2–3×，输出分布数学上等价于直接用大模型解码

与 PagedAttention 的协同：Draft token 分配投机 KV block → 被拒绝则释放（分页代价极低）→ 被接受则提升为正式 block。Block Table 更新仅需修改 $O(k)$ 条映射。

2.2.6 70B 模型推理显存预算计算

Llama-3 70B, BF16, 8×A100-80GB (TP=8)：

$$\begin{aligned} \text{模型权重} &= 70 \times 10^{9} \times 2\text{B} = 140 \text{ GB} \div 8 = 17.5 \text{ GB/卡} \\ \text{KV Cache 可用} &= 80 - 17.5 - 3\text{(激活+系统)} = 59.5 \text{ GB/卡} \\ \text{每 token KV (TP=8 后)} &= 2 \times 80 \times 1 \times 128 \times 2 = 40{,}960 \text{ B} \approx 40 \text{ KB} \\ \text{最大容纳 token 数} &= \frac{59.5 \times 10^{9}}{40{,}960} \approx 1{,}452{,}000 \text{ tokens} \\ \text{128 并发 × 4096 长度} &= 524{,}288 \text{ tokens → 余量充足} \end{aligned}$$

无 PagedAttention 时碎片浪费约 50%，同等条件仅能跑约 64 条并发——吞吐直接减半。

2.2.7-2.2.8 端到端系统与架构

vLLM 的工程实现采用经典的异步 Producer-Consumer架构：

  • 前端：异步 API Server（兼容 OpenAI 格式）→ Tokenizer → 请求入队
  • 调度层：Scheduler 每步从 Waiting/Running/Swapped 三队列中选择最优 batch 组合
  • 执行层：Model Executor（管理 TP Workers）+ PagedAttention Kernel + KV Block Manager
  • 输出层：Detokenizer → SSE Streaming → 客户端

2.2.9 vLLM 核心组件详解

  • API Server：基于 FastAPI，兼容 OpenAI Chat/Completions 接口，支持 streaming 和 tool calls
  • Scheduler：vLLM 的"大脑"，维护 Waiting / Running / Swapped 三队列。调度策略：优先级 + FCFS + 预算约束（不超过 max_num_seqs 和显存上限）。支持 preemption：显存不足时将低优先级序列 swap 到 CPU
  • Block Manager：实现虚拟内存抽象——分配、释放、Copy-on-Write、Swap to CPU、Prefix Caching 查找
  • Model Executor：封装 TP/PP 逻辑；调用 PagedAttention CUDA kernel（支持 Flash Attention 后端）
  • KV Block Pool：启动时预分配所有物理 block（默认 16 token/block），运行时零动态内存分配

2.2.10 请求生命周期

  1. 请求到达 API Server → tokenize → 加入 Waiting Queue
  2. Scheduler 检查可用 block 数 → 满足则移入 Running Queue，分配初始 KV blocks
  3. Prefill 阶段：一次前向处理所有 prompt tokens，填充 KV Cache
  4. Decode 阶段：每步生成 1 token，追加 KV 到当前 block（block 满则分配新 block）
  5. 生成 EOS 或达到 max_tokens → 移出 Running → 释放所有 block 回 Free List
  6. 若中途显存紧张 → Scheduler 可选择 preempt：将序列 KV blocks swap 到 CPU DRAM → 移入 Swapped Queue → 空闲时 swap 回继续

2.2.11 Prefix Caching（自动前缀缓存）

利用 LLM 应用中大量请求共享相同前缀（如系统提示）的特征：

  1. 对每个物理 block 的 token 内容计算 hash
  2. 新请求到达时逐 block 查询缓存：hash 命中 → 跳过该 block 的 prefill 计算，直接复用物理 KV
  3. 命中的 block 标记引用计数 +1（Copy-on-Write 保护）
  4. 淘汰策略：LRU，仅在显存压力时释放最久未用的缓存 block
效果：对于 2K+ token 共享系统提示的聊天场景，Prefix Caching 可将 TTFT（Time-To-First-Token）降低 60–80%，等效 prefill 计算量减少 50%+。

2.2.12 Guided (Constrained) Decoding——结构化输出

vLLM 原生支持受约束解码，保证输出语法上合法（如合法 JSON、匹配正则）：

  • 原理：模型输出 logits 后、采样前，用 FSM/PDA 状态机生成 mask，屏蔽不合法 token 的 logit 为 $-\infty$
  • 约束类型：JSON Schema、正则表达式、EBNF 文法、枚举选择（Choice）
  • 引擎后端：XGrammar（默认 v0.7+，C++ 实现的下推自动机）；Outlines（FSM 回退方案）
  • 性能影响：mask 操作 <1 ms/step，吞吐量损失 <2%
  • Schema 编译：首次 0.5–5s（复杂 schema 更久），之后跨请求复用缓存
注意：结构化输出 ≠ 正确输出。Constrained Decoding 只保证"语法合法"（能 parse 为合法 JSON），不保证"语义正确"——模型仍可能生成合法但事实错误的字段值。

关键要点总结

  1. GPU 的本质：用海量并行线程换取高吞吐，代价是单线程延迟高。LLM 的矩阵乘天然匹配。
  2. 内存层次决定一切：Registers → SRAM → L2 → HBM，每级带宽跌 10 倍。所有优化本质都是"少搬数据"。
  3. Roofline 模型：算术强度 $I$ vs 屋脊点 $I_{\text{ridge}}$，一算就知道瓶颈在计算还是内存。
  4. Attention = memory-bound, FFN = compute-bound：不同层需要不同策略（Flash Attention vs 量化）。
  5. Tensor Core 只在 compute-bound GEMM 时有效；batch=1 推理回到 memory-bound 无法利用。
  6. 通信拓扑决定并行策略：NVLink 内 TP=8；IB 跨节点 DP/FSDP；PP 连接层间。
  7. KV Cache 碎片是推理的主要显存瓶颈。PagedAttention 用分页消除碎片，利用率 20% → 95%。
  8. Continuous Batching：以单步为粒度动态增删序列，GPU 永不空等，吞吐翻倍。
  9. Speculative Decoding：小模型猜、大模型验，延迟降 2–3×，质量数学证明无损。
  10. Prefix Caching + CoW：共享前缀只存一份，TTFT 降低 60–80%。
  11. Guided Decoding：logits mask 实现结构化输出，性能影响 <2%。

Q&A 自测

Q1：为什么说"理解内存层次是所有优化的根基"？

因为几乎所有 GPU 上的 LLM 优化——Flash Attention、量化、KV Cache 分页、梯度累积——本质都在做同一件事：减少从慢存储读写的字节数。GPU 的计算力远超其"喂数据"的能力：A100 可以每秒 312 万亿次运算，但显存只能喂 2 TB/s。如果不理解 Registers → SRAM → L2 → HBM → CPU 的带宽阶梯（每级跌 10 倍），就无法判断 kernel 瓶颈在哪，更无法选择正确的优化手段。

Q2：Flash Attention 的核心 trick 是什么？为什么让 Attention 从 memory-bound 变成 compute-bound？

标准 Attention 将 $n \times n$ 的注意力矩阵 $S = QK^T$ 写入 HBM 再读回（对 $n=4096$ 约 138 MB 流量），导致算术强度仅 62 FLOP/Byte。Flash Attention 的核心是SRAM 内 tiling：将 Q/K/V 按行方向切成小块，每块完全在 192KB SRAM 内完成 softmax 融合计算（用 online softmax 技巧处理数值稳定性），永不将 $n \times n$ 矩阵写回 HBM。HBM 流量降至仅读写 Q/K/V/O ≈ 4 MB → 算术强度从 62 飙到 2048 FLOP/Byte，超过屋脊点 13 倍。

Q3：为什么 Tensor Core 在 batch=1 推理时几乎无用？

Tensor Core 是矩阵乘加速器（4×4×4 MMA），高效前提是 GEMM 的 M/N/K 维度足够大以填满 tile，且整体是 compute-bound。batch=1 时，输入维度 M=1（本质是矩阵-向量乘），tile 大部分为空。更关键的是：需要从 HBM 读取全部权重（70B=140GB）却只做 1 token 计算，算术强度约 $2 \times 70 \times 10^9 / (140 \times 10^9) = 1$ FLOP/Byte，远低于屋脊点 156。kernel 完全 memory-bound，Tensor Core 再快也只能空等数据。

Q4：PagedAttention 和操作系统虚拟内存有何异同？

相似：逻辑连续 → 物理不连续的映射；固定大小的"页"；页表做翻译；支持 CoW 和 Swap。
差异：(1) OS 用硬件 MMU/TLB 做地址翻译，PagedAttention 是纯软件（在 attention kernel 中 gather）；(2) OS 页 4KB，PagedAttention block 默认 16 tokens（物理大小 ~640KB）；(3) LLM KV Cache 是只追加的（序列生成方向单调递增），不存在随机写入，比通用虚拟内存场景简单高效得多。

Q5：Continuous Batching 为什么依赖 PagedAttention？

Continuous Batching 每步都要动态增删序列：序列结束释放内存，新序列加入需要分配。如果 KV Cache 连续分配，移除序列后留下外部碎片，新序列比空洞长就放不进去——要么做昂贵的 defrag，要么浪费空间。PagedAttention 的 block 全等大、可互换：释放即回池、分配即取块，$O(1)$ 完成，完美匹配"每步有序列进出"的需求。

Q6：Speculative Decoding 为什么不影响输出质量？

关键在于验证步用原始大模型做 rejection sampling。Draft 模型只负责产生候选；大模型一次前向 pass 给所有候选打分，用 $\min(1, p_{\text{target}}(x)/p_{\text{draft}}(x))$ 的接受概率逐 token 判定。数学上可证明：被接受的序列分布与直接用大模型逐 token 采样完全一致。最坏情况只是猜错浪费了 draft 模型的计算，绝不会接受大模型不认可的 token。

Q7：NVLink 和 InfiniBand 分别解决什么问题？为什么 TP 只在 NVLink 内？

NVLink 解决节点内 GPU 间高带宽通信（H100: 900 GB/s 双向）；InfiniBand 解决节点间通信（NDR: 50 GB/s/port）。Tensor Parallelism 在每层的前向/反向中都做 AllReduce，通信频率极高（每层 2 次）。若走 IB (50 GB/s) 而非 NVLink (900 GB/s)，通信时间膨胀 18×，成为严重瓶颈。因此 TP 只在 NVLink 互连的同节点内使用。而 Data Parallelism 只在每训练步结尾做一次梯度 AllReduce（可与计算重叠），能容忍 IB 的较低带宽。

Q8：Guided Decoding 的 mask 操作为什么几乎不影响吞吐？

因为 mask 发生在模型前向 pass 完成之后。模型的重计算（attention + FFN，数百 TFLOP）已结束，输出一个 vocab_size 大小的 logits 向量。约束引擎只需根据当前 FSM/PDA 状态查预计算的合法 token 集合，将不合法位设为 $-\infty$——这是一次 $O(\text{vocab\_size})$ 的 mask 操作，与前向计算相比完全可忽略（<1ms vs 前向 ~50ms）。Schema 编译成本（0.5–5s）仅首次请求承担，后续复用缓存。

Q9：如何判断一个新的 GPU kernel 是 compute-bound 还是 memory-bound？

三步判断法：(1) 数 FLOPs：统计 kernel 的总浮点运算次数；(2) 数 Bytes：统计 kernel 需要从 HBM 读写的总字节数；(3) 计算算术强度 $I = \text{FLOPs} / \text{Bytes}$，与目标 GPU 的屋脊点 $I_{\text{ridge}}$ 比较。若 $I < I_{\text{ridge}}$（A100 BF16 为 156），kernel 是 memory-bound——优化方向是减少数据搬运（融合 kernel、tiling、减少中间结果写入）。若 $I > I_{\text{ridge}}$，kernel 是 compute-bound——优化方向是用更低精度（FP8/INT8）或更大 tile 提升 Tensor Core 利用率。

Q10：为什么推理引擎要"拼命凑大 batch"？

单序列推理（batch=1）时，每步需要从 HBM 读取全部模型权重（70B=140GB），但只计算 1 个 token 的前向——算术强度约 1 FLOP/Byte，GPU 利用率 < 1%。当 batch=B 时，同一份权重被 B 个序列复用，算术强度变为 $\sim B$ FLOP/Byte。要让 GPU 达到峰值性能需要 $B \geq I_{\text{ridge}} = 156$（A100 BF16）——即 batch ≥ 156 才能让 Tensor Core 跑满。这就是 Continuous Batching 和 PagedAttention 凑大 batch 的本质动力。
