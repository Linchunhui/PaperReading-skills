第21章：Model Context Protocol (MCP)

模型上下文协议——AI工具集成的USB-C标准，实现LLM与外部世界的统一连接

来源：Agentic AI · 第21章（pp. 392–410） · 阅读笔记

章节摘要

Model Context Protocol（MCP）是由Anthropic于2024年底发布的开放标准协议，旨在解决AI系统与外部工具、数据源之间碎片化集成的根本问题。正如USB-C统一了物理接口，MCP为LLM与外部能力之间提供了一个标准化的通信层。本章从动机出发，深入解析MCP的三角色架构（Host/Client/Server）、核心原语（Tools/Resources/Prompts/Sampling）、JSON-RPC 2.0协议规范、安全模型、Python实现模式，以及与替代方案（OpenAI Function Calling、LangChain等）的对比。最后探讨MCP如何服务于Agent训练——标准化的动作空间与轨迹记录为强化学习提供了理想的环境接口。

21.1 Motivation: The Tool Integration Problem

在MCP出现之前，每个AI应用都面临M×N集成问题：如果有M个AI模型/应用、N个外部工具/数据源，则需要编写M×N个定制连接器。这产生了大量重复工作、不一致的接口设计、以及难以维护的集成代码。

碎片化的代价

  • 开发者负担：每接入一个新工具都需要从头编写适配代码，处理认证、错误处理、数据格式转换等
  • 不一致性：不同工具的集成方式差异巨大——有的用REST API，有的用SDK，有的用CLI
  • 安全漏洞：各自为政的集成缺乏统一的安全模型，权限控制参差不齐
  • 可复用性差：为一个AI平台编写的工具集成无法直接迁移到另一个平台
$$C_{\text{integration}} = M \times N \times c_{\text{connector}}$$

其中 $M$ 是AI应用数量，$N$ 是外部工具数量，$c_{\text{connector}}$ 是单个连接器的开发维护成本。MCP将其降为 $M + N$：每个应用实现一个MCP Client，每个工具实现一个MCP Server。

USB-C类比

核心洞察：正如USB-C为物理设备提供了统一接口（一根线连接显示器、充电器、硬盘等），MCP为AI系统提供了统一的"数字接口"。工具提供者只需实现一次MCP Server，就可以被任何支持MCP的AI应用调用；AI应用只需实现一个MCP Client，就能连接任何MCP Server。

21.2 Architecture Overview

Three-Role Model（三角色模型）

MCP定义了三个核心角色，各司其职：

角色职责典型实现
Host用户直接交互的AI应用，管理安全策略和用户授权Claude Desktop、VS Code Copilot、IDE插件
Client维护与Server的1:1连接，处理协议层通信SDK中的MCP Client类（嵌入Host中）
Server暴露特定能力（工具/资源/提示），连接实际外部系统文件系统Server、数据库Server、GitHub Server

Transport Layers（传输层）

MCP支持两种传输机制，适应不同部署场景：

传输方式适用场景特点
stdio本地Server（子进程）Host启动Server进程，通过stdin/stdout交换JSON-RPC消息；零网络开销，安全隔离好
HTTP + SSE远程Server（网络服务）Client通过HTTP POST发送请求，Server通过Server-Sent Events推送响应/通知；支持跨网络部署

Protocol Lifecycle（协议生命周期）

  1. Initialize：Client发送initialize请求，包含协议版本和客户端能力声明
  2. Negotiate：Server回复支持的能力（tools/resources/prompts/sampling）
  3. Initialized：Client发送initialized通知确认，连接就绪
  4. Operation：正常的请求-响应和通知交换阶段
  5. Shutdown：任一方可发起优雅关闭

Stateful vs. Stateless

设计选择：MCP是有状态协议。一旦连接建立，Client和Server之间维护持久会话。Server可以缓存上下文、跟踪资源订阅、并向Client推送变更通知。这与无状态的REST API形成对比——MCP优化的是持续的交互式协作，而非一次性请求。

21.3 Core Primitives

MCP定义了四类核心原语（Primitives），覆盖了AI与外部世界交互的所有维度：

Tools（工具）

工具是MCP中最核心的原语——允许LLM执行操作（副作用）。工具类似于函数调用：有明确的输入schema、执行逻辑和输出结果。

  • 控制方：Model-controlled（模型决定何时调用）
  • 类比：POST请求——可能改变外部状态
  • 示例：execute_sql、send_email、create_github_issue

Resources（资源）

资源提供只读的上下文数据，不产生副作用。模型或应用可以请求资源来丰富自己的上下文。

  • 控制方：Application-controlled（应用侧决定何时获取）
  • 类比：GET请求——幂等、只读
  • 示例：file://project/src/main.py、db://users/schema
  • 支持订阅：Client可订阅资源变更通知

Prompts（提示模板）

预定义的提示模板，帮助用户以标准化方式与特定领域交互。

  • 控制方：User-controlled（用户选择使用哪个模板）
  • 用途：将最佳实践编码为可复用的交互模式
  • 示例：review_code（代码审查模板）、explain_error（错误解释模板）

Sampling（采样）

最独特的原语——允许Server反向请求LLM生成。这打破了传统的单向调用模式，使Server能够利用LLM的推理能力。

  • 控制方：Server-initiated（Server主动请求Host中的LLM）
  • 用途：让工具Server在执行过程中"思考"——例如，代码分析Server请求LLM解释错误模式
  • 安全约束：所有Sampling请求必须经过Host的用户授权审批

四原语对比总结

原语方向控制者副作用类比
ToolsClient → ServerModel有POST / 函数调用
ResourcesClient → ServerApplication无GET / 文件读取
PromptsClient → ServerUser无模板 / Snippet
SamplingServer → ClientServer视情况回调 / 反向RPC

21.4 Protocol Specification

JSON-RPC 2.0

MCP建立在JSON-RPC 2.0之上，这是一个轻量级的远程过程调用协议。所有消息均为JSON格式，分为三类：

// Request（请求）——带有id，期望响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "execute_sql",
    "arguments": {
      "query": "SELECT * FROM users LIMIT 10"
    }
  }
}

// Response（响应）——匹配请求id
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "| id | name | email |\n|---|---|---|\n| 1 | Alice | alice@example.com |"
      }
    ]
  }
}

// Notification（通知）——无id，不期望响应
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": {
    "uri": "file://project/config.yaml"
  }
}

Capability Negotiation（能力协商）

连接建立时，双方通过initialize交换能力声明：

// Client → Server: initialize request
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "sampling": {},           // Client支持Sampling
      "roots": { "listChanged": true }
    },
    "clientInfo": {
      "name": "claude-desktop",
      "version": "1.2.0"
    }
  }
}

// Server → Client: initialize response
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": { "subscribe": true, "listChanged": true },
      "prompts": { "listChanged": true }
    },
    "serverInfo": {
      "name": "postgres-server",
      "version": "0.5.0"
    }
  }
}

Error Handling（错误处理）

MCP使用JSON-RPC标准错误码，并扩展了特定于协议的错误：

错误码含义场景
-32700Parse ErrorJSON格式无效
-32600Invalid Request不符合JSON-RPC 2.0规范
-32601Method Not Found调用不存在的方法
-32602Invalid Params参数不符合schema
-32603Internal ErrorServer内部执行错误

Progress Reporting（进度报告）

对于长时间运行的操作，Server可以通过通知发送进度更新：

{
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "op-123",
    "progress": 45,
    "total": 100,
    "message": "Processing file 45 of 100..."
  }
}

21.5 Tool Definition and Discovery

Schema Format（Schema格式）

MCP工具使用JSON Schema定义输入参数，确保类型安全和自描述性：

{
  "name": "execute_sql",
  "description": "Execute a read-only SQL query against the connected database. Returns results as formatted text. Use for data retrieval only.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "The SQL SELECT query to execute"
      },
      "database": {
        "type": "string",
        "description": "Target database name",
        "default": "main"
      },
      "limit": {
        "type": "integer",
        "description": "Maximum rows to return",
        "default": 100,
        "maximum": 1000
      }
    },
    "required": ["query"]
  }
}

最佳实践：工具的description字段至关重要——它是LLM决定是否使用该工具的主要依据。应明确说明：(1) 工具做什么；(2) 适用场景；(3) 限制条件。避免模糊描述如"执行操作"。

Dynamic Registration（动态注册）

MCP支持运行时工具列表的动态变更。Server可以在连接存续期间添加/移除工具，并通过notifications/tools/list_changed通知Client重新拉取工具列表：

// Server通知Client工具列表已变更
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}

// Client随后调用 tools/list 获取最新工具列表

Annotations（注解）

工具注解为Host提供额外的元信息，帮助做出安全和用户体验决策：

{
  "name": "delete_file",
  "description": "Permanently delete a file from the filesystem",
  "annotations": {
    "destructive": true,         // 破坏性操作——需要用户确认
    "idempotent": false,         // 非幂等——重复调用有不同效果
    "readOnlyHint": false,       // 非只读——会修改外部状态
    "openWorldHint": true        // 开放世界——可能影响外部系统
  },
  "inputSchema": { ... }
}

21.6 Security Model

Trust Hierarchy（信任层级）

MCP建立了清晰的三层信任模型：

  • User：拥有最终决策权，所有敏感操作需用户确认
  • Host：代表用户执行安全策略，过滤和审批Server请求
  • Server：被视为不可信的第三方代码，其输出需要验证，其请求需要授权

User Consent（用户同意）

MCP的安全模型要求"human-in-the-loop"——关键操作必须经过用户明确授权：

  1. 首次连接Server时，Host向用户展示Server声明的能力
  2. Server请求Sampling时，Host必须获取用户批准
  3. 带有destructive: true注解的工具调用需二次确认
  4. 用户可以随时撤销Server的特定能力权限

Input Validation（输入验证）

关键安全原则：Server绝不能信任来自Client的输入。即使Client发送的参数通过了JSON Schema验证，Server仍必须进行业务逻辑层面的验证——检查路径遍历攻击、SQL注入、命令注入等。MCP的schema验证是第一道防线，但绝非唯一防线。

Credential Management（凭证管理）

  • 凭证（API key、token）永远不应通过MCP协议传输
  • Server使用自有的凭证管理（环境变量、secret store）
  • Host不应向Server暴露用户的认证信息
  • OAuth流程通过独立的安全通道完成，不走MCP消息

Sandboxing（沙箱隔离）

  • 每个Server进程在独立的沙箱中运行
  • 文件系统访问限定为声明的roots范围
  • 网络访问可通过Host策略限制
  • Server之间不能直接通信——必须通过Host中转

21.7 Implementation Patterns

Server in Python（Python实现Server）

以下是一个功能完整的MCP Server示例，展示了工具定义、资源暴露和错误处理：

import asyncio
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import (
    Tool, TextContent, Resource,
    GetPromptResult, PromptMessage
)

# 创建Server实例
app = Server("demo-server")

# ========== 工具定义 ==========
@app.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="word_count",
            description="Count words in a given text string",
            inputSchema={
                "type": "object",
                "properties": {
                    "text": {
                        "type": "string",
                        "description": "Text to count words in"
                    }
                },
                "required": ["text"]
            }
        ),
        Tool(
            name="file_search",
            description="Search for files matching a glob pattern",
            inputSchema={
                "type": "object",
                "properties": {
                    "pattern": {
                        "type": "string",
                        "description": "Glob pattern (e.g., '**/*.py')"
                    },
                    "root_dir": {
                        "type": "string",
                        "description": "Root directory to search from",
                        "default": "."
                    }
                },
                "required": ["pattern"]
            }
        )
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    if name == "word_count":
        text = arguments["text"]
        count = len(text.split())
        return [TextContent(
            type="text",
            text=f"Word count: {count}"
        )]
    elif name == "file_search":
        import glob
        pattern = arguments["pattern"]
        root = arguments.get("root_dir", ".")
        matches = glob.glob(pattern, root_dir=root, recursive=True)
        return [TextContent(
            type="text",
            text="\n".join(matches[:50])  # 限制返回数量
        )]
    else:
        raise ValueError(f"Unknown tool: {name}")

# ========== 资源定义 ==========
@app.list_resources()
async def list_resources() -> list[Resource]:
    return [
        Resource(
            uri="config://server/status",
            name="Server Status",
            description="Current server health and configuration",
            mimeType="application/json"
        )
    ]

@app.read_resource()
async def read_resource(uri: str) -> str:
    if uri == "config://server/status":
        import json
        return json.dumps({
            "status": "healthy",
            "uptime_seconds": 3600,
            "tools_registered": 2
        }, indent=2)
    raise ValueError(f"Unknown resource: {uri}")

# ========== 启动Server ==========
async def main():
    async with stdio_server() as (read_stream, write_stream):
        await app.run(read_stream, write_stream)

if __name__ == "__main__":
    asyncio.run(main())

Client Implementation（Client实现）

from mcp.client import ClientSession
from mcp.client.stdio import stdio_client, StdioServerParameters

async def run_client():
    # 配置Server进程
    server_params = StdioServerParameters(
        command="python",
        args=["demo_server.py"],
        env={"PYTHONPATH": "."}
    )
    
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            # 1. 初始化连接
            await session.initialize()
            
            # 2. 发现可用工具
            tools = await session.list_tools()
            print(f"Available tools: {[t.name for t in tools.tools]}")
            
            # 3. 调用工具
            result = await session.call_tool(
                "word_count",
                arguments={"text": "Hello world from MCP"}
            )
            print(f"Result: {result.content[0].text}")
            
            # 4. 读取资源
            resource = await session.read_resource("config://server/status")
            print(f"Server status: {resource.contents[0].text}")

asyncio.run(run_client())

Error Recovery（错误恢复）

MCP Client应实现健壮的错误恢复策略：

  • 重连机制：Server进程崩溃时，Client应自动重启并重新初始化
  • 超时控制：每个工具调用设置合理超时（如30s），超时后返回错误而非无限等待
  • 降级处理：当特定Server不可用时，Host应继续运行（减少能力但不完全失败）
  • 幂等重试：对于标记为idempotent: true的工具，可安全重试失败的调用

When to Use MCP（何时使用MCP）

推荐使用MCP的场景：

  • 构建需要连接多个外部系统的AI应用（M×N问题明显时）
  • 需要跨不同AI平台复用同一套工具集成
  • 安全性要求高，需要进程隔离和用户授权控制
  • 工具集动态变化，需要运行时发现和热加载
  • 团队协作中，希望工具开发与AI应用开发解耦

不需要MCP的场景：

  • 只使用单一模型平台（如仅用OpenAI），Function Calling足够
  • 工具逻辑简单且固定，不需要进程隔离
  • 延迟极度敏感的场景（进程间通信有额外开销）

Migration Paths（迁移路径）

  1. 从Function Calling迁移：将现有函数定义转换为MCP Tool schema，将实现逻辑封装为MCP Server
  2. 从LangChain迁移：将LangChain Tool包装为MCP Server，保留原有逻辑，添加schema和传输层
  3. 渐进式采用：在现有架构中逐步引入MCP Server，先从独立性强的工具开始（如文件系统、搜索），逐步扩展

21.10 MCP for Agent Training

MCP不仅是生产部署的集成标准，更是Agent训练的理想基础设施。其标准化的接口定义为强化学习提供了规范的环境抽象。

RL Environment Interfaces（强化学习环境接口）

MCP天然适配RL训练中的"环境"概念：

$$\text{MDP}: \mathcal{M} = (\mathcal{S}, \mathcal{A}, T, R, \gamma)$$

将MCP映射到MDP：状态$\mathcal{S}$对应Resources提供的上下文，动作$\mathcal{A}$对应Tools的调用，转移函数$T$由Server执行结果决定，奖励$R$可从执行反馈推导。

# MCP作为RL环境的接口抽象
class MCPEnvironment:
    """将MCP Server包装为Gymnasium兼容的RL环境"""
    
    def __init__(self, server_params: StdioServerParameters):
        self.session = None
        self.server_params = server_params
    
    async def reset(self) -> dict:
        """重置环境，返回初始观测（Resources）"""
        # 重新连接Server
        self.session = await self._connect()
        # 初始观测 = 所有资源的当前状态
        resources = await self.session.list_resources()
        obs = await self._gather_observations(resources)
        return obs
    
    async def step(self, action: dict) -> tuple:
        """执行动作（Tool调用），返回(obs, reward, done, info)"""
        tool_name = action["tool"]
        arguments = action["arguments"]
        
        try:
            result = await self.session.call_tool(tool_name, arguments)
            obs = self._parse_result(result)
            reward = self._compute_reward(result)
            done = self._check_termination(result)
            return obs, reward, done, {"success": True}
        except Exception as e:
            return {}, -1.0, False, {"error": str(e)}
    
    @property
    def action_space(self) -> list:
        """动作空间 = 所有可用工具及其参数schema"""
        return self._cached_tools

Standardized Action Spaces（标准化动作空间）

MCP的工具schema为RL Agent提供了精确定义的动作空间：

  • 结构化动作：每个工具的inputSchema定义了该动作的参数空间，天然支持类型约束
  • 动态动作集：通过tools/list，Agent可以在运行时发现可用动作，适应环境变化
  • 动作注解：destructive、idempotent等元信息帮助RL训练策略设计exploration策略
$$\pi_\theta(a|s) = \text{LLM}_\theta\big(\text{tool\_call} \mid \text{context}(s), \text{tools\_schema}\big)$$

策略$\pi_\theta$即LLM在给定上下文状态$s$和工具schema的条件下，生成工具调用$a$的概率分布。MCP保证了tools_schema的标准化格式，使得同一Agent可以无修改地跨不同MCP Server训练。

21.11 Summary

Key Takeaways

  • MCP解决M×N问题：通过标准协议将集成成本从$O(M \times N)$降至$O(M + N)$，实现工具与应用的解耦
  • 三角色架构：Host管理安全、Client管理连接、Server暴露能力——职责清晰，信任分层
  • 四类原语：Tools（执行动作）、Resources（提供数据）、Prompts（标准化交互）、Sampling（反向LLM调用）
  • JSON-RPC 2.0：轻量级、语言无关的协议基础，支持请求/响应/通知三种消息模式
  • 安全第一：不可信Server模型 + 用户授权 + 进程隔离 + 凭证不穿透
  • 生态爆发：从文件系统到数据库到SaaS API，MCP Server生态快速扩展
  • 训练友好：标准化接口天然构成RL环境，协议消息直接可作为训练轨迹

Q&A 深度问答

Q1: MCP与传统REST API的本质区别是什么？为什么不直接用REST？

本质区别在三个维度：(1) 有状态性——MCP维护持久连接和会话上下文，REST是无状态的请求-响应；(2) 双向通信——MCP支持Server主动推送通知和Sampling请求，REST是严格的客户端驱动；(3) 语义标准化——MCP定义了统一的工具发现、能力协商和安全模型，REST只规定了HTTP动词语义。REST适合简单的数据CRUD，MCP适合复杂的AI-工具交互协作。

Q2: Sampling原语的实际使用场景是什么？为什么Server需要反向调用LLM？

典型场景：(1) 智能数据转换——数据库Server收到查询结果后，请求LLM将原始数据总结为自然语言描述；(2) 动态工具生成——代码分析Server发现新的API后，请求LLM生成对应的工具描述；(3) 错误诊断——Server执行出错时，请求LLM基于错误上下文生成修复建议；(4) 多步推理——复杂工具需要中间推理步骤（如规划SQL查询策略），Server可请求LLM"思考"。关键约束是所有Sampling都经Host审批，防止Server滥用LLM资源。

Q3: MCP的有状态设计是否会带来可靠性问题？如何处理连接中断？

有状态确实引入可靠性挑战，MCP通过以下机制应对：(1) 自动重连——Client检测到连接断开后自动重启Server进程并重新初始化；(2) 幂等性标记——带idempotent: true的工具可安全重试；(3) 进度恢复——长操作通过progressToken可在重连后查询状态；(4) 优雅降级——Host不依赖单一Server，某Server不可用时其他Server继续服务。实践中，对于关键操作，建议设计为"可检查状态+可安全重试"模式。

Q4: 如何设计一个安全的MCP Server？有哪些必须避免的安全反模式？

必须做的：(1) 验证所有输入参数，即使已通过schema校验；(2) 限制文件访问在声明的roots内；(3) 对SQL查询使用参数化语句；(4) 对外部命令执行进行白名单控制；(5) 设置操作超时。必须避免的反模式：(1) 在工具中暴露环境变量或内部凭证；(2) 允许任意路径访问（路径遍历）；(3) 将用户输入直接拼接到shell命令；(4) 信任Client声称的用户身份；(5) 在错误消息中泄露内部实现细节。

Q5: MCP如何支持Agent的工具学习？从"不会用工具"到"熟练使用"的训练路径是什么？

MCP为Agent工具学习提供了完整的基础设施：第一阶段（SFT）——使用人类专家的MCP交互轨迹做监督微调，让Agent学会基本的工具调用格式和常见使用模式；第二阶段（RL Exploration）——将MCP Server作为RL环境，Agent通过trial-and-error学习最优工具使用策略。由于MCP的schema提供了精确的动作空间定义，exploration更高效（不需要猜测参数格式）；第三阶段（Continual Learning）——当新MCP Server上线时，Agent通过schema的自描述性快速适应新工具，无需重新训练。

Q6: 在多Server架构中，Host如何路由请求？如果多个Server提供同名工具怎么办？

Host维护一个工具注册表，记录每个工具来自哪个Server。路由策略：(1) 命名空间隔离——实践中建议工具名带Server前缀（如github.create_issuevsjira.create_issue）；(2) 优先级配置——Host可配置同名工具的优先级；(3) 能力合并——将所有Server的工具列表合并后统一呈现给LLM，由LLM根据description选择最合适的。对于真正冲突的情况，规范建议Host在初始化时检测并向用户报告命名冲突。

Q7: MCP的性能开销如何？相比进程内函数调用，延迟增加了多少？

stdio传输的典型开销：(1) 进程启动——首次连接时启动Server进程，Python约200-500ms，Node.js约100-300ms（仅一次）；(2) 单次调用——序列化→管道传输→反序列化约增加1-5ms延迟（相比进程内调用的微秒级）；(3) 内存——每个Server进程独立占用内存（Python进程约30-80MB）。HTTP+SSE传输额外增加网络RTT。总体来说，对于LLM应用（单次推理本身需要数百ms到数秒），MCP的额外1-5ms开销可以忽略不计。真正的性能瓶颈在LLM推理本身，而非协议层。

Q8: MCP协议的未来演进方向是什么？有哪些已知的局限性正在被解决？

当前已知局限和演进方向：(1) 认证标准化——当前版本缺乏标准的OAuth/OIDC集成流程，2025年版本将内建身份认证支持；(2) Streamable HTTP——新传输层替代SSE，支持更灵活的双向流式通信；(3) Server-to-Server——允许MCP Server之间直接通信（当前必须经Host中转）；(4) Registry标准——标准化的Server发现和版本管理协议；(5) 性能优化——批量调用（batch requests）和消息压缩。MCP正从"协议规范"演进为"完整平台"。
