第19章：Agent Design Patterns

Agent设计模式——从Workflow到Autonomous Agent的规范架构

来源：Agentic AI · 第19章（pp. 369–374） · 阅读笔记

章节摘要

构建有效的agent不仅需要强大的模型和工具集。架构——LLM如何被编排、任务如何分解、控制流如何在组件间流动——决定了agent是否可靠、可调试和成本可控。本章呈现从Anthropic、OpenAI、Google以及开源社区的生产部署中涌现的规范设计模式。

核心区分：Agents vs. Workflows

关键决策原则：不是所有任务都需要自主agent。首先尝试workflow；只有当任务确实需要动态路由或开放式探索时，才升级为agent。

维度WorkflowAgent
控制流预定义，LLM在特定步骤被调用LLM动态决定下一步做什么
优势可预测、可测试、更便宜灵活，处理新颖情况
适用场景任务结构已知需要自适应决策

19.1 Workflow Patterns

这些模式改编自Anthropic的agentic构建模块分类法[342]——在预定义控制流中使用LLM。系统（而非模型）决定执行顺序。

19.1.1 Prompt Chaining（提示链）

定义：最简单的模式——将复杂任务分解为固定序列的LLM调用，将一次调用的结果作为下一次调用的上下文输入。步骤之间的验证门（validation gates）在错误向下游传播之前尽早捕获。

适用场景：自然顺序性的任务——内容生成、数据转换、多阶段分析。

核心优势：每一步可以使用不同的prompt、模型或temperature。中间结果可检查、可调试。

执行流程：Input → LLM Call 1 → Gate ✓ → LLM Call 2 → Gate ✓ → LLM Call 3 → Output。Gate可以是LLM-based的（让另一个LLM评判质量）或programmatic的（规则检查）。

19.1.2 Routing（路由）

定义：一个分类器（LLM或传统ML）检查输入并分派到专门化的处理器。输入被分类一次，然后由对应的专家处理。

适用场景：不同任务类型需要不同最优prompt、工具或模型的场景——客户支持分流、多模态输入处理。

执行流程：Input → Classifier → Route A / Route B / Route C → 各自用专门化的prompt和工具处理。

19.1.3 Parallelization（并行化）

定义：多个LLM调用并发运行，由程序化层组合其输出。存在两种子模式：

  • Sectioning（扇出）：将输入分割为不相交的块并独立处理每一块——例如同时对代码库运行安全检查、性能检查和风格检查。
  • Voting（冗余）：以不同seed或temperature发出相同prompt N次，然后通过多数投票、Reward Model打分或LLM-as-judge选择最佳结果。

示例：代码审查

  1. 并行调用：Security review ∥ Performance review ∥ Style review
  2. 聚合：合并所有发现，去重，按严重程度排序

延迟优势：Latency = $\max(\text{individual calls})$ 而非 $\sum(\text{individual calls})$

19.1.4 Orchestrator-Workers（编排器-工作者）

定义：LLM自身决定如何拆分工作。Orchestrator模型分析任务、产出子任务计划、将每个子任务分派给Worker LLM（可能使用不同的prompt或工具），最终将Worker的输出合并为连贯结果。

与Parallelization的关键区别：分解逻辑是模型生成的（model-generated），而非硬编码的。

适用场景：开放式问题，子任务的数量和性质在设计时无法枚举——例如"重构这个代码库"需要先理解依赖图才能决定修改哪些文件。

执行流程：Task → Orchestrator LLM（生成计划）→ Worker 1 / Worker 2 / Worker N（并行执行）→ Orchestrator（合并结果）→ Final Output

19.1.5 Evaluator-Optimizer（评估器-优化器）

定义：一个双模型反馈循环[240]——Generator产出候选输出，而独立的Evaluator根据明确标准评分。如果分数低于阈值，Evaluator的批评被追加到Generator的上下文中，循环重复直到质量标准满足或重试预算耗尽。

适用场景：具有明确质量标准的任务——必须通过测试的代码、必须保留语义的翻译、必须匹配风格指南的写作。

$$\text{Loop: } \text{Output}_i = \text{Generator}(\text{prompt} + \text{critique}_{i-1}) \;\rightarrow\; \text{Score}_i = \text{Evaluator}(\text{Output}_i, \text{criteria})$$

如果 $\text{Score}_i < \text{threshold}$，则将critique反馈给Generator进入下一轮迭代。这实现了无需权重更新的迭代精炼（test-time refinement）。

19.2 Autonomous Agent Patterns

这些模式将执行流的控制权交给LLM本身。

19.2.1 ReAct（Reason + Act）

定义：基础性的Agent模式[127]。LLM在思考（内部推理）、行动（工具调用）和观察（处理结果）之间交替循环，直到产出最终答案。

ReAct实现要点：

  • Scratchpad："Thought"步骤被记录但不展示给用户
  • Tool parsing：Harness从模型输出中提取结构化工具调用
  • Max iterations：始终为循环设上限（典型值：10–25次迭代）
  • Termination：模型输出特殊动作（如 final_answer）或未检测到工具调用

循环结构：Thought → Action → Observation → Thought → Action → Observation → ... → Final Answer

19.2.2 Planning Agents（规划型Agent）

定义：Agent在执行前生成显式计划，并可在执行过程中修改计划[126]。计划是一个"活文档"——提供结构但适应观察。Harness将依赖关系跟踪为DAG，只执行前驱已完成的步骤。

规划策略何时重新规划特征
Plan-then-Execute从不简单；对意外结果脆弱
Adaptive失败时仅在步骤失败时重新规划；适中成本
Continuous每一步每次观察后全面重评估；昂贵但健壮
Hierarchical子计划完成时高层计划固定；子计划动态生成

示例：研究报告生成

用户请求："写一份2页报告，比较用于时间序列预测的Transformer架构。"

Step 1 — 计划生成（单次LLM调用）：

plan = [
  {"id": 1, "task": "搜索近期transformer时间序列模型(2023-2025)", "tool": "search_web", "deps": []},
  {"id": 2, "task": "阅读top 5论文，提取关键方法", "tool": "read_papers", "deps": [1]},
  {"id": 3, "task": "构建对比表（架构、数据集、指标）", "tool": "none", "deps": [2]},
  {"id": 4, "task": "撰写引言+方法论", "tool": "none", "deps": [2]},
  {"id": 5, "task": "撰写结果+结论", "tool": "none", "deps": [3, 4]},
  {"id": 6, "task": "审阅并润色", "tool": "none", "deps": [5]}
]

Step 2 — 带自适应重规划的执行：Agent按依赖顺序执行步骤。步骤1后搜索仅返回3篇相关论文。Agent重新规划：添加子步骤扩展搜索到邻近领域（如PatchTST、iTransformer）。修改后的计划从步骤2继续。

关键洞察：计划是活文档，提供结构但适应观察。Harness将依赖追踪为DAG，只执行前驱已完成的步骤。

19.2.3 Reflection and Self-Critique（反思与自我批评）

定义：Agent暂停来评估自身轨迹并纠正方向。三个层级：

  1. Output validation："这是否正确？我是否遗漏了什么？"
  2. Trajectory review：回顾最近k步，识别错误或低效。
  3. Strategy revision：重新考虑整体方法（"我是否在解决正确的问题？"）

Reflexion模式[224]：维护一个持久的"反思记忆"。每次失败尝试后，agent写下自然语言反思（"我失败了因为我没有检查边界情况"）。下次尝试时，这些反思被包含在prompt中——实现无需权重更新的跨episode学习。

19.2.4 Tool-Use Patterns（工具使用模式）

定义：Agent如何调用工具显著影响其可靠性、延迟和成本。五种规范模式[332]：

模式描述示例
Single-turn每次LLM响应一个工具调用简单的搜索Q&A
Multi-tool (Parallel)一次响应中多个并行工具调用Search + Calculate + Format
Sequential (Pipeline)工具输出作为下一个工具的输入Search → Read → Extract
Nested (Agent-as-Tool)工具调用触发另一个agent代码agent调用test-runner
Fallback首选工具失败；尝试替代方案API → Scrape → Cache

各模式详解

Single-Turn：最简单——模型发出一次工具调用，接收结果，产出最终答案。Harness恰好进行两次LLM调用（一次决定工具，一次合成结果）。适用于事实查找、单位转换或单API查询。

Multi-Tool (Parallel)：现代API（OpenAI、Anthropic）允许模型在单次响应中请求多个工具调用。Harness并发执行并一起返回所有结果。关键约束：工具必须独立（无工具的输出作为另一工具的输入）。极大减少需要来自多源独立信息的任务延迟。

Sequential (Pipeline)：每个工具的输出作为下一个工具的输入，形成数据管线。模型根据前一结果决定下一工具。常见于研究工作流：search → fetch_page → extract_data → analyze。Harness需跟踪增长的上下文，可能需要摘要化中间结果以控制预算。

Nested (Agent-as-Tool)：工具调用启动一个完全独立的agent——有自己的prompt、工具和上下文。父agent将子agent视为黑盒函数。Swarm模式[336]通过专门化agent间的handoff来泛化此模式。

Fallback (Graceful Degradation)：Harness按优先级顺序尝试工具：首选工具失败（超时、限速、API错误）→ 自动回退到替代方案。模型无需感知回退逻辑——Harness透明处理。示例：primary search API → backup search → cached results → 通知模型搜索不可用。

19.3 Design Principles

以下原则摘自Anthropic构建有效agent的指南[342]，适用于所有模式：

  1. 保持简单（Keep it simple）：使用最简单的可行架构。只在被证明必要时增加复杂性。能用prompt chain解决的问题，永远优于可能有用的multi-agent系统。
  2. 透明优于聪明（Transparency over cleverness）：每一步应可检查。避免隐藏状态或隐式推理。当agent失败时你需要理解原因——不透明的架构使调试不可能。
  3. 提供好工具（Provide good tools）：文档清晰、类型完善、错误信息明确的工具是力量倍增器。模糊描述的工具会被误用；精确schema和使用指导的工具会被正确选择。
  4. 为失败做计划（Plan for failure）：每次工具调用都可能失败。在harness层构建重试逻辑、回退和优雅降级，使模型无需推理基础设施故障。
  5. 使用结构化输出（Use structured outputs）：约束生成（JSON schema、function calling）防止解析失败。产出需要regex解析的自由文本的agent是脆弱的；产出经验证的JSON的agent是健壮的。
  6. 用多样输入测试（Test with diverse inputs）：Agent行为比单轮chat更具变异性。相同prompt可在不同运行中产出不同工具调用序列。用边界案例、歧义请求和畸形输入进行对抗性测试。

19.4 Pattern Selection Guide

选择正确模式取决于三个因素：(1) 任务结构的可预测性；(2) 延迟和成本预算允许多少LLM调用；(3) 质量是否需要迭代。使用下表作为决策矩阵——从顶部（最简单）开始，只在更简单的模式明显失败时才向下移动。

模式复杂度LLM调用数最佳适用
Prompt ChainingLowN（固定）顺序任务、内容管线
RoutingLow1+1多类型输入、分流
ParallelizationLowN（并行）独立子任务、投票
Orchestrator-WorkersMedium可变未知分解方式
Evaluator-OptimizerMedium2–10（循环）质量关键输出
ReActMedium3–25（循环）通用工具使用、探索
Planning AgentHigh5–50+长时程、多步骤任务
ReflectionHigh+50%开销首次尝试常失败的任务
Multi-AgentHigh大量复杂领域、专门化分工

模式可组合：Planning Agent可能在单个步骤中使用Prompt Chaining，在审查阶段使用Evaluator-Optimizer，用Routing将子任务分派给专家。艺术在于知道何时停止添加层次。

核心要点

  • Workflow优先：从最简单的模式开始（Prompt Chaining），只在更简单的模式无法满足需求时才升级复杂度
  • 5种Workflow模式：Prompt Chaining → Routing → Parallelization → Orchestrator-Workers → Evaluator-Optimizer（系统控制流）
  • 4种Autonomous模式：ReAct → Planning → Reflection → Tool-Use（模型控制流）
  • 6条设计原则：简单性、透明性、好工具、容错、结构化输出、多样测试
  • 模式可组合：复杂系统由多种模式嵌套构建——关键是知道何时停止叠加
  • 决策矩阵：根据任务结构可预测性、成本预算和质量迭代需求选择模式

Q&A 自测

Q1：Workflow和Agent模式的根本区别是什么？

根本区别在于控制权归属：Workflow模式中，系统（而非模型）决定执行顺序——LLM在预定义的步骤中被调用；Agent模式中，LLM自身动态决定下一步做什么——执行流的控制权交给了模型。

Q2：Orchestrator-Workers与Parallelization有什么本质区别？

本质区别在于分解逻辑的来源：Parallelization的分解是硬编码的（设计时确定如何分割任务），而Orchestrator-Workers的分解是模型生成的（LLM自身分析任务并决定如何拆分）。这使得Orchestrator-Workers适用于开放式问题，其中子任务的数量和性质在设计时无法枚举。

Q3：Reflexion模式如何实现"无需权重更新的学习"？

Reflexion维护一个持久的"反思记忆"：每次失败后，agent将失败原因写为自然语言反思并存储。下次尝试时，这些历史反思被注入prompt——模型通过上下文中的历史教训来避免重复错误。这在效果上等同于"学习"，但无需任何梯度下降或权重更新——纯粹通过上下文工程（in-context learning）实现。

Q4：为什么"保持简单"是第一条设计原则？

因为Agent系统的复杂性带来指数级增长的调试难度、不可预测性和成本。一个能用Prompt Chain解决的问题，如果用Multi-Agent系统来实现，会引入协调开销、通信失败、状态同步等大量新的故障点。更简单的架构更可预测、更容易测试、更便宜运行。只在简单方案被证明无法胜任时，才逐步增加复杂度。

Q5：如何选择合适的Agent设计模式？

根据三个因素判断：(1) 任务结构可预测性——结构已知用Workflow，需要动态决策用Agent；(2) LLM调用预算——延迟和成本约束决定能承受多少次调用；(3) 质量是否需要迭代——需要反复精炼用Evaluator-Optimizer或Reflection。决策策略是从表的顶部（最简单）开始，只在更简单模式明显失败时才向下移动。
