导读：架构定型之后，七篇论文各自往哪使劲

此前 OCR 系列笔记的结论是：“动态分辨率视觉端 + 0.5–4B 小 LLM”这套零件已经定型，竞争焦点从架构搬到了数据引擎、RL 策略、是否解耦布局三件事。2026 年 4 月到 7 月的七篇新工作几乎都在印证并推进这件事，还冒出一条更清晰的新主线：怎么把“一页文档一个字一个字吐出来”这件慢事变快。

文档输出又长又结构化，自回归解码成为死穴。新工作分两路夹攻：一路压低每一步计算——Unlimited-OCR 用 R-SWA 把 KV cache 从随长度线性增长压成常数；另一路缩短解码步数——HunyuanOCR-1.5 用 DFlash 投机解码，P-MTP 一次预测多个 token，HPD-Parsing 则把整页拆成可以并行的分支。与此同时，OvisOCR2 用 0.8B 端到端模型第一次登上 OmniDocBench v1.6 榜首，MonkeyOCRv2 则回到最底层，重造文档原生视觉骨干。

①PaddleOCR-VL-1.5 百度 · 2026-04

0.9B 架构全面升级布局引擎，新增 Seal / Text Spotting，野外文档 Real5 拿到 92.05。

PaddleOCR-VL-1.5: Towards a Multi-Task 0.9B VLM for Robust In-the-Wild Document Parsing

出发点

初代 PaddleOCR-VL 在干净扫描件上已经很强，但布局引擎仍是“矩形检测 + 独立指针网络排阅读序”。碰到歪斜、卷翘、手持拍照等非平面文档，矩形框锚不准，阅读序又依赖分步后处理，一步错就会层层放大。真实落地还缺公章识别和 Text Spotting 两类能力。

方法详解

PP-DocLayoutV3 从 RT-DETR 改来：Mask 检测头取代矩形框；阅读序直接集成进 Transformer 解码层；布局类别扩到 25 类。阅读序先算两个元素谁应该在前：

$$S_{i,j}=\frac{f(q_i,q_j)-f(q_j,q_i)}{\sqrt{d_h}},\qquad f(q_i,q_j)=(W_q q_i)^\top(W_k q_j)$$

白话翻译：对任意两个版面元素，分别算“i 在 j 前”和“j 在 i 前”的分数，做差后得到相对先后置信度。反对称设计保证判断自洽，再用全局投票恢复整页阅读序。

SFT 阶段用 UACS 决定每个视觉聚类要采多少样本，让扭曲公章、密排表格等“难但重要”的数据自动获得更多训练时间，而不是被大量简单样本淹没。

关键发现

OmniDocBench v1.5 Overall 从 92.86 升到 94.50。Real5-OmniDocBench 加权平均 92.05，其中 Skew +14.19、Screen Photography +9.22、Warping +5.28。Seal NED 0.138，优于 Qwen3-VL-235B 的 0.382。

②PaddleOCR-VL-1.6 百度 · 2026-06

架构不变，用欠优化区域挖掘与渐进式后训练把 0.9B 推到 OmniDocBench v1.6 96.33。

PaddleOCR-VL-1.6: Expanding the Frontier of Document Parsing with Under-Optimized Region Refinement and Progressive Post-Training

出发点

VL-1.5 的残余错误不是随机分布，而是集中在三种系统性区域：对 checkpoint 或轻微视觉扰动敏感的边界脆弱区；古籍、稀有字符、工业表格等覆盖稀疏区；模型很自信但标签本身错误的监督不可靠区。结论是：紧凑模型不该无差别扩数据，而要定向修补弱区。

方法详解

数据引擎从训练末期多个 checkpoint 和多种语义不变扰动中找不稳定样本，用密度导向渐进聚类发现小而孤立的稀疏分量，再由 Qianfan-OCR、GLM-OCR、MinerU2.5-Pro 三个专家交叉投票修正监督。最关键的工程动作是把候选表格或公式重新渲染成图，再与原图视觉比对，避免文本级比较误判。

后训练分 CPT → SFT → RL。RL 只挑“偶尔能做对但还没稳定”的高潜力样本：

$$\operatorname{Score}(x)=\big(r_{\max}(x)-r_{\mathrm{mean}}(x)\big)\exp\!\big(\alpha U(x)+\beta V_r(x)\big)$$

白话翻译：最好 rollout 明显高于平均值，说明模型已经摸到正确路径；不确定性和奖励方差越大，GRPO 越有学习信号。太难、太简单或奖励完全相同的样本都会被过滤。

关键发现

OmniDocBench v1.6 Overall 96.33，Real5 93.19，Hard Table TEDS 91.71。消融从 94.93 出发：CPT +0.69，SFT +0.63，RL 仅 +0.08，说明主要收益来自数据引擎而非 RL。

③Unlimited-OCR 百度 · 2026-06

视觉和 prompt token 永远可见，输出只看最近 n 个 token，把 KV cache 从 O(T) 压成 O(1)，一次前向解析 40+ 页。

出发点

标准自回归 decoder 每写一个字都要回看前面所有输出，KV cache 随长度线性膨胀。DeepSeek-OCR 已经压缩了视觉 token，但长输出下 decoder 的全注意力仍是瓶颈。

直觉：人抄书时会一直盯着原书，但只需要关心刚刚写下的几个字。视觉证据应该常驻，旧输出则可以软遗忘。

方法详解

R-SWA 把可见范围切成两块：视觉 token 与 prompt 作为固定前缀，全程可见；生成内容只保留最近 n 个 token 的滑动窗口。普通 SWA 会把视觉 token 一起挤出窗口，而 R-SWA 把证据钉住。

$$C_{\text{R-SWA}}(T)=L_m+\min(n,T)\le L_m+n$$

白话翻译：$T$ 是已生成长度，$L_m$ 是固定视觉前缀，$n$ 是窗口宽度。标准全注意力 cache 是 $L_m+T$，R-SWA 永远不超过 $L_m+n$，所以文档再长也不会继续涨。

关键发现

全部 MHA 换成 R-SWA 不仅没有掉精度，OmniDocBench v1.5 还比同架构 DeepSeek-OCR 高 6.22 分；v1.6 拿到 93.92。6000 个解码 step 上，标准 MHA 单步从 9μs 涨到 16μs，R-SWA 一直保持 9μs。一次前向解析 40+ 页时质量缓慢退化但没有崩溃，主要失败来自小字分辨率而非窗口失忆。

④HunyuanOCR-1.5 腾讯混元 · 2026-07

不大改骨架，用 DFlash、Agentic Data Flow 和 RL 同时变快变强，端到端 SOTA 94.74。

HunyuanOCR-1.5: Making Lightweight OCR VLMs Faster and Better

出发点

扫描财报往往包含几千字、跨页大表和多行公式，逐 token 解码让单页耗时达到 34.85 秒。OCR VLM 还普遍缺低资源语言、古文字和复杂表格数据，且容易把看不清的字脑补成合理词。

方法详解

DFlash 让草稿模型一次并行提出一整块候选，大模型一次验证并接受最长合法前缀，输出分布仍与原模型一致。块内越靠后的 token 越难猜，因此训练时位置权重指数衰减，让模型先学稳近处，再逐渐延伸有效接受长度。Agentic Data Flow 用 agent 搜材料、调用工具质检和生成数据，覆盖 331 种语言。RL 则分别评价文本、表格与公式，避免一把编辑距离误判结构化元素。

$$R_{\text{parse}}=\lambda_1R_{\text{text}}+\lambda_2\frac1M\sum_{j=1}^{M}R_{\text{elem}}(e_j)$$

白话翻译：总奖励把文本正确性和表格、公式等结构元素分开评。表格看内容与结构，公式使用更适合数学表达的指标；超长截断或末尾复读直接判为硬伤。

关键发现

DFlash 让单页 Transformer 从 34.85 秒降到 5.47 秒（6.37×），表格提速 7.81×。古文字平均分 0.54，OmniDocBench v1.6 端到端 SOTA 94.74。作者同时用 CHAOS-Bench 揭示短板：模型仍很难忠实抄写“看得见但语义无效”的乱码，语言先验会驱动脑补。

⑤MonkeyOCRv2 华科 + 金山 · 2026-07

“看图写字 + 像素重建”双目标，为文档重造视觉编码器。

MonkeyOCRv2: A Visual-Text Foundation Model for Document AI

出发点

自然图像视觉编码器习惯抹掉“不影响物体类别”的局部变化，但文档的语义恰恰藏在半个字符、一根笔画和表格边界里。模型把 e^{iπ}=-1+0i 脑补成常见的 e^{iπ}=-1，不是没语言能力，而是视觉特征没保住 +0i。

方法详解

视觉 token 分两路：文本解码器负责“看图写字”，视觉解码器负责重建原图。前者让特征理解文字内容，后者逼它保住字形、笔画与版面细节。

$$\mathcal L_{\text{pretrain}}=\mathcal L_{\text{text}}+\lambda\mathcal L_{\text{rec}}$$

白话翻译：文本损失教模型懂内容，重建损失阻止它只靠上下文猜答案。两者一起把“语言先验捷径”堵住，让视觉证据真正进入表示。

关键发现

在五类文档任务上替换成 MonkeyOCRv2 编码器都能涨点。0.1B 视觉端配 0.6B LLM，在 MDPBench 得到 83.3，超过视觉端大约 11 倍的 dots.mocr。把文字顺序打乱后，去掉重建的准确率从 99.7 崩到 55.4，加上重建仍有 72.1，直接证明重建在对抗语言先验作弊。

⑥OvisOCR2 阿里 · 2026-07

0.8B 端到端第一次登顶 OmniDocBench v1.6，双管数据引擎与老师 RL → 学生蒸馏是胜负手。

OvisOCR2 Technical Report

出发点

流水线先做版面分析，再识别区域。一旦第一步把复杂表格当成插图漏掉，下游识别再强也无法恢复，错误会跨阶段累积且不可逆。端到端模型直接看整页输出 Markdown，结构更干净，却长期在榜单上落后。

方法详解

真实数据用专用解析器生成结构化标注并做子集级抽检；合成数据由同一份 HTML 同时导出 Markdown 标注和渲染图，实现“源头即真相”。小模型直接 RL 容易出现 KL 飙升和表格崩坏，因此先让 4B 老师做 RL，再用在线策略蒸馏把能力传给 0.8B 学生，最后融合多个变体。

$$R(y,y^*)=\frac{\sum_{c\in\mathcal C}a_c(y^*)s_c(y,y^*)}{\sum_{c\in\mathcal C}a_c(y^*)}$$

白话翻译：只对参考答案中真实存在的文本、表格和公式求平均。一页没有公式，就不会因为缺少公式分被惩罚；结构解析失败或截断则把对应组件直接清零。

关键发现

OmniDocBench v1.6 总分 96.58，第一次让端到端模型登顶。复杂表格集上，流水线会整张漏掉 13–17% 的表，OvisOCR2 只漏 7.96%，验证了端到端消除不可逆版面误差的价值。短板是 PureDocBench Real 轨道只有 66.56，退化真实图仍不够稳。

⑦HPD-Parsing（含 P-MTP）百度 · 2026-07

把整页单条自回归轨迹换成层级并行解码，峰值 4752 TPS，达到自回归基线 3.06×。

HPD-Parsing: Hierarchical Parallel Document Parsing · P-MTP

出发点

统一 VLM 虽然把整页作为一个输入，输出仍沿单一 token-by-token 轨迹生成。长输出时解码耗时可以达到视觉编码的约 496 倍。版面结构需要全局协调，但每个区域内容主要依赖自己的视觉块，因此没有必要让所有内容串行。

方法详解

主布局分支按阅读序生成元素类别、坐标和 <FORK> 路由 token；遇到 <FORK> 就动态创建内容分支，并行解码对应区域。多个分支复用视觉前缀 KV，只看自己的局部历史。分支内部再接 P-MTP，一次草拟多个未来 token，训练时对越远、越不可靠的预测降低权重。

$$\mathcal L=\sum_{k=0}^{K}\frac{\sum_{t=0}^{N}\mathcal M_{t+k+1}\mathcal W_{t,k}\ell(\hat p_t^k,y_{t+k+1})}{\sum_{t=0}^{N}\mathcal M_{t+k+1}}$$

白话翻译：$k=0$ 是普通 next-token，$k\ge1$ 是一次往前多猜几步。距离越远、路径或目标越不一致，权重越低；先学稳近处，再逐渐解锁远处预测。推理时平均每步接受 6.6 个 token。

关键发现

OmniDocBench v1.6 Overall 94.91，ReadOrderEdit 0.124 为全表最好。吞吐从 1554.8 TPS 升到 4752.1 TPS（3.06×），PPS 从 1.02 升到 2.68。最长输出桶中解码步数最多节省 18.04×，延迟降低 5.80×。P-MTP 深度并非越大越好：9 步是速度、接收率与草稿开销的平衡点，18 步反而变慢。

贯穿线：四条把七篇串起来的暗河

线 1：提速成为主战场

路线一是减少每一步计算：DeepSeek-OCR 先压视觉 token，Unlimited-OCR 再用 R-SWA 把 decoder cache 压成常数。路线二是减少解码步数：DFlash 投机解码、P-MTP 多 token 预测、HPD-Parsing 层级并行。共同前提是文档输出局部规律强、熵低，所以表格、公式与长输出的收益最大。

线 2：端到端扳回一城

此前 OmniDocBench 前列长期由流水线占据。OvisOCR2 用 0.8B 端到端模型第一次登顶 96.58，并用漏表率揭示流水线的结构性问题：版面阶段漏掉的区域，下游无法恢复。PaddleOCR-VL-1.6 仍以 96.33 紧追，两种路线还会长期并存。

线 3：架构冻结，数据和训练成为胜负手

PaddleOCR-VL-1.6、HunyuanOCR-1.5、OvisOCR2 都没有大改骨架，而是把杠杆压在难例挖掘、多专家共识、渲图验证、教师 RL 和蒸馏上。唯一反向者 MonkeyOCRv2 回到视觉底座，提醒我们上层调不动时，文档视觉编码器的目标错配可能才是天花板。

线 4：忠实度成为公开难题

CHAOS-Bench 和 MonkeyOCRv2 的乱码实验都在问同一件事：模型是在照抄看见的字，还是用语言先验脑补一个合理答案？当前绝对水平仍低。像素重建辅助目标给出了一个可迁移方向：让模型保留视觉证据，堵住语言捷径。

三句话总结

  1. 这一批在做什么：在小型 OCR VLM 架构已相对稳定的基础上，把文档解析往更快、更鲁棒、更忠实三个方向推进。
  2. 走到了哪里：OvisOCR2 端到端达到 96.58 并首次登顶；HPD-Parsing 达到 3.06× 自回归吞吐；HunyuanOCR-1.5 把单页从 34.85 秒降到 5.47 秒；Unlimited-OCR 一次前向覆盖 40+ 页。
  3. 核心方法论：胜负手正在从换架构转向定向数据引擎、教师 RL / 蒸馏和新解码范式，而视觉骨干错配与“照抄而非脑补”的忠实度，是下一程仍未解决的地基问题。
