# 六字段和问题签名

| 字段 | 应回答的问题 | 避免混入 |
|---|---|---|
| `background` | 任务为什么存在、目前在什么情境下重要？ | 无关的领域百科或宣传 |
| `direction` | 本文处在什么研究方向或任务范围？ | 仅在相关工作出现的方向；尚未确认的分类 ID |
| `problem` | 现有办法具体卡在哪里，本篇要改变什么？ | 方法名称、笼统的“效果不好” |
| `approach` | 作者打算怎样绕开/消除该瓶颈，为什么？ | 逐层实现细节或未经证实的因果承诺 |
| `methods` | 输入是什么、关键步骤如何运行、得到什么输出？ | 只罗列组件名称和性能数字 |
| `summary` | 本文解决了什么、机制与证据是什么、结论到哪里为止？ | 复制原摘要、堆砌所有消融 |

每项用 `{item_id, text, basis, evidence}`，局部 ID 在本篇唯一。`paraphrase` 为输入支持的转述；`inference` 为读者的解释或推断，正文明确“据此推测/一种解释是”，不能以作者口吻陈述。方向名称是有证据的自然语言归纳；正式 taxonomy 分类交给分类步骤，不在这里创造权威分类 ID。

条目数不固定。一个清楚的机制可以用一个条目；复杂流程可分成数个有关联的条目。字符串可含 Markdown 与 LaTeX。公式沿用输入中能确认的定义；文字提及某公式但公式缺失时写缺失，不根据记忆补造版本。玩具例子只能明确标为解释性例子，不进入 `results` 当实验数据。

## results 与 reported_limitations

`results` 记录支撑结论的关键实验、定理或测量发现，含足够的模型、任务、指标和评测条件。需要全面指标库时复用元数据抽取的 benchmark 记录，这里无需再次穷举全部表格。

`reported_limitations` 是论文明确承认或展示的边界；推测的弱点不能伪装成作者已报告的限制。必要推断可放在带 `basis: inference` 的 `summary` 中。顶层 `limitations` 描述输入覆盖和本次分析的限制，二者不要混淆。

## problem_signatures

这是后续判断“是否研究同一类问题”的可追溯输入，不是最终聚类结果。每条包括：

- `problem_item_ids`：本篇 `problem` 中所描述的问题 ID。
- `objective`：要提高/降低/证明/测量什么。
- `input`、`output`：任务对象与目标产物；理论工作可写数学对象与待证明性质。
- `bottleneck`：为什么现有方案无法达到目标。
- `constraints`：改变问题定义或可行方案的条件，例如低标注、在线部署、固定算力、长文档；没有证据不填。
- `evidence`：支持上述签名的输入片段。

未知内容用 `null` 或 `[]`。问题签名是归纳，不能增添输入没提过的约束。“效率优化”太宽：训练省显存、解码低延迟、数据少标注可能是不同问题。相同 benchmark 不保证问题相同，不同模型家族也不代表问题不同。

一篇论文同时解决两个问题时保留两条签名，避免把二者合成一个含糊目标。后续可按问题分组，而非强制一篇只能有一个标签。

## missing_fields

`path` 为从 `/data` 开始的 JSON Pointer，`reason` 取 `absent_from_input / explicitly_unreported / conflicting / partial_coverage`。说明缺失如何影响理解；不要把“输入未给出”写成“论文没有做”。核心字段有空缺、输入为摘要片段或存在未解决的机制冲突时标为 `status: partial`。
