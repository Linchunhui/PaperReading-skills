# 输入证据与精简

## 建立最小证据链

先检查输入覆盖，再阅读所提供的引言、相关工作、方法、实验、消融、讨论/局限和关键附录。表格错位或公式缺失时，若输入含截图则对照；否则记录缺失与不确定，不凭残缺文本猜数字，也不默认重新获取 PDF。

临时证据笔记按需要记录以下项目即可，无需先做大型结构化数据库：

| 项目 | 核对信息 |
| --- | --- |
| 身份与覆盖 | 标题、作者、年份、版本、来源、已读部分与缺失部分 |
| 问题与前作 | 应用任务、障碍、前人思路、已解决部分、缺口、来源章节 |
| 核心机制 | 输入、关键变换、输出、设计理由、训练/推理区别、关键公式与符号 |
| 主结果 | 对照、模型/数据/预算、评测协议、指标方向、原始值、定位 |
| 消融/诊断 | 改了什么、保持什么不变、观察值、支持的判断、混杂与限制 |
| 配图 | asset ID、已有图号/页码、内容用途、图注、是否实际查看清晰度与边界 |

JSON 中所有核心判断用 input-contract.md 的 unit 引用；只有输入明确带有这些定位时，显示文字才可写成 `§3.2 / Table 4 / Fig. 2 / PDF p.6`，页码说明是 PDF 页序号还是印刷页码。缺少稳定页码的 HTML 可用节号、图表号和原文链接。不要伪造页码。

先查输入中的相关工作与引用上下文。未提供前作原文时注明这是本文作者对前作的描述，不自动补搜前作或扩展成文献综述。用户另行要求外部补充时，独立标注新增来源。

结构化笔记也是允许的输入，但只能验证到它所提供的记录；保留上游证据，不把生成摘要引用升级为亲自核验原论文。无材料支持的结构、实验、复杂度、作者意图或缺陷不补写。

## 核心结论与证据强度

对改变论文理解的核心主张，在已有证据笔记中补一句“该证据实际支持什么、不能推出什么”。不要求逐句建表或另建证据图谱。

- **作者解释或主张：** 论文提出的动机、解释与推测，写成“作者认为/提出”，不能因出现在论文中就当作已验证机制。
- **实验观察：** 说明在什么设置下观察到何种结果。相关趋势、单条生成样例或多个条件同时改变的比较，不能证明某组件的独立因果作用。
- **受控对照支持：** 核对改变的因素、保持不变的条件及重复实验信息，再限定结论范围。没有误差条或统计检验时不声称统计显著。
- **理论支持：** 保留关键假设与结论适用范围，不把定理延伸成论文未验证的实际效果。

同一主张可同时有几类证据。证据只支持较窄范围时，收窄正文措辞；证据缺失时明确缺口。正文用自然语言保留必要限定，不强制给每句话贴证据等级标签。

## 先保证理解，再减少字数

精简的是阅读成本，不能精简证据标准。按以下顺序修改：

1. **闭合方法链。** 补齐输入、关键操作、输出及设计动机之间的断点。
2. **保留所有核心贡献。** 合并重复叙述，次要结果可归并；不偷换成“每篇只讲一个卖点”。
3. **用动词代替名词串。** 把“引入对齐模块实现多尺度融合”改写为具体对象如何被变换和组合，前提是原文确实如此。
4. **压缩外围内容。** 删领域通史、长作者名单、重复 benchmark、无助理解的实现细节、套路式结语。
5. **检查每句的信息增量。** 背景、图注、方法和结尾避免重复同一个结论。

最短版本仍应让读者知道“实际做了什么”。必要术语首次出现时用一句或一个短语解释；类比只能帮助理解，不能替代真实操作。数学符号的解释不能只停留在变量名称。

不按固定字数给每个章节或每篇论文平均分配篇幅。卡片应简洁且易扫描，机制复杂就合理拆卡；总结应连贯，必要步骤多就展开。用户明确要求上限时计数并标明口径，不能静默截断。

## 事实、解释与借鉴分层

- **论文报告：** 有直接表格、公式、图或文字支持。
- **讲解者解释：** 用白话解释现有机制，不额外引入未证实的因果关系。
- **待验证借鉴：** 从论文推导的应用假设，写明迁移条件和需要验证的点。

摘要尽量集中在已证实的论文内容。粗读可给借鉴建议，但不要把“可以尝试”写成“在你的任务上会提升”。对于“首次”“通用”“SOTA”等表述，限定比较集合和实际验证范围。

交付时准确说明来源覆盖。全文不可得可以交付带标签的暂定摘要或局部分析，并明确缺口；不能宣布已完成全文阅读。图像或公式还未正确显示时，说明交付仍缺什么。
