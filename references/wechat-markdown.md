## 产物与命名

默认让每份 HTML 带一份适合公众号编辑器继续排版的 Markdown：

- `paper.html` → `paper.wechat.md`
- `JEPA.html` → `JEPA.wechat.md`
- `2026-08-06-radar.html` → `2026-08-06-radar.wechat.md`
- Markdown 图片放到同目录的 `{HTML stem}.wechat-assets/`

只有用户明确说“只要 HTML”时才省略 Markdown。Markdown 不是完整 HTML 的机械转写，而是基于同一证据重新组织的精简文章。

## 内容压缩

先写一句文章承诺：读完能知道什么。然后只保留支撑这句承诺的内容。

默认长度：

- 单篇：1800–3500 中文字
- 系列：2500–4500 中文字
- 随笔：每篇 500–900 字，总计不超过 5000 字
- 日报：1800–3500 字
- 周报：3000–5500 字

压缩顺序：

1. 删 Related Work 的完整谱系，只保留理解本论文必需的 1–2 个前作。
2. 删复现级超参、次要消融和重复 benchmark。
3. 方法只保留“输入 → 关键动作 → 输出”以及为什么这么设计。
4. 实验保留 1–3 个能改变判断的结果；数字精度保持与论文一致。
5. Q&A、完整引用、长 limitation 列表默认不进公众号版。
6. 公式优先改写为白话；只有公式本身承重时才保留一条。

不得为了缩短而删掉限定条件、对比口径或证据边界。Markdown 里的数字和结论必须与 HTML、论文原文一致。

## 文章结构

推荐 5 段结构，不强行套十节笔记：

```markdown
# {能看懂主题的标题}

{80–150 字导语：具体场景 + 文章承诺}

## 为什么要做这件事
{现实痛点与前作卡点}

## 作者用了什么办法
{输入、关键机制、输出；2–4 个短段落}

## 实验真正说明了什么
{1–3 个关键结果 + 限定条件}

## 这项工作的边界
{没证明什么、在哪些条件下可能失效}

## 最后记住这三点
1. ...
2. ...
3. ...

## 参考资料
[1] ...
```

系列模式可把中间部分改成“第一代 → 第二代 → 最新一代”；随笔和雷达可用“本期先看三件事 → 每篇短卡 → 本期结论”。

## 移动端排版

- 只用一个 `#` 主标题，正文主要使用 `##`；最多到 `###`。
- 每段 2–4 句，通常 60–140 个中文字符。手机屏幕避免一整屏只有一个段落。
- 每节只加粗 1–2 个真正承重的短语，禁止整段加粗。
- 列表控制在 3–5 项；超过 5 项就分组或改成短段落。
- 引用块只放结论、提醒或限定条件，不放长篇论文原文。
- emoji 默认不用；确有栏目感时每个一级区块最多一个。
- 不写侧边目录、折叠 Q&A、悬浮元素或依赖 CSS 的复杂结构。
- 开头不重复摘要和 Motivation；导语只负责把读者拉进一个问题。

## 图片、公式与表格

### 图片

- 每篇公众号文章保留 1–3 张承重图。
- 优先选择架构总览、核心结果和一张解释机制的图。
- 从 base64 HTML 转换时，把图片释放到 `.wechat-assets/` 并在 Markdown 使用相对路径。
- 每张图前用一句话告诉读者“看哪里”，图后用一句话给结论。
- SVG 在发布前转成 PNG；如果当前环境不能可靠转换，宁可省略或换原论文位图。
- 不把 base64 直接塞进 Markdown；多数公众号编辑器会造成体积过大或上传失败。

### 公式

- 公众号版优先保留白话翻译，删除推导过程。
- 必须保留时使用标准 `$...$` / `$$...$$`，并紧跟一句白话。
- 发布前在目标编辑器检查公式能力；doocs/md 支持 KaTeX，文颜支持数学公式。

### 表格

- 手机端默认不使用超过 3 列的表格。
- 复杂对照表改写成“论文名：关键变化”的项目列表。
- 数字对比优先写成短句或配一张图，不把完整实验表搬进文章。

## 链接与证据

微信公众号正文中的外链体验有限，因此默认把链接改成文末编号参考：

```markdown
论文原文[1]给出的主结果是……

## 参考资料

[1] 论文标题：https://arxiv.org/abs/...
```

- 论文/PDF/项目页排在媒体解读前。
- 正文里只保留必要编号，不连续堆三个链接。
- 不引用 HTML 本地路径作为读者来源。
- Markdown 末尾注明“本文基于论文与项目页整理”，但不写空泛免责声明。

## 转换流程

### HTML 与 Markdown 同时生成

1. 先从同一份论文证据写完整 HTML。
2. 按本文件重新选择公众号叙事，不从 HTML 逐段删字。
3. 输出 `{stem}.wechat.md`，保留 1–3 张图片到 `.wechat-assets/`。
4. 对照 HTML 核验标题、数字、结论、限定条件和来源。

### 单独把 HTML 转成公众号 Markdown

先运行确定性提取：

```bash
python3 scripts/html_to_markdown.py "input.html" --compact
```

脚本默认输出 `input.wechat.md`，释放 base64/内联 SVG 到 `input.wechat-assets/`，删除 TOC、Q&A、关键引用等不适合公众号的结构，并把外链整理成文末参考。

随后必须做一次语义精简：重写导语，合并重复段落，把十节笔记压成 4–6 个公众号小节，并核对数字。脚本负责格式转换，不替代这一步判断。

## 参考项目

排版与兼容策略参考以下开源项目，但 PaperStudio 不强依赖其中任何一个：

- [doocs/md](https://github.com/doocs/md)：标准 Markdown、KaTeX、代码高亮、自定义主题与图片上传；作为默认兼容目标。
- [caol64/wenyan](https://github.com/caol64/wenyan)：多平台发布、链接转脚注、公式、代码高亮、front matter 与主题系统。
- [lyricat/wechat-format](https://github.com/lyricat/wechat-format)：列表样式和链接转文末索引的处理思路；项目已停止维护，只参考设计。
- [nicejade/markdown-nice](https://github.com/nicejade/markdown-nice)：自定义样式与跨内容平台排版。
- [geekjourneyx/md2wechat-skill](https://github.com/geekjourneyx/md2wechat-skill)：面向 Agent 的 inspect/preview/convert 与发布前 readiness 思路；高级 API/发布能力属于可选外部工具。

默认输出保持标准 Markdown，确保可以直接导入 doocs/md 或文颜；不要默认写某个项目专属的扩展语法。

## 验收清单

- 文件名为 `{HTML stem}.wechat.md`。
- 开头 150 字内出现具体问题和文章承诺。
- 正文 4–6 个主要小节，没有照搬完整十节目录。
- 关键数字与 HTML/论文一致，保留比较口径。
- 只保留 1–3 张承重图，图片使用相对路径且文件存在。
- 没有 base64 图片、侧边 TOC、折叠 Q&A 或大段 HTML/CSS。
- 复杂表格已改写，公式已白话化。
- 外链集中到文末参考资料。
- 在 doocs/md 或同类标准 Markdown 编辑器中预览无明显破版。
