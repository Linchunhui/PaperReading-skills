# 雷达发现 / radar

发现、筛选与解释指定方向的论文，形成日/周/月报告；也可整理用户给定的跨方向候选集合。完整读取 paper-storyline、per-paper-deep-read、directions 与 [radar-writing.md](radar-writing.md)。**每篇正式收录论文默认提供可独立理解的讲解。先走通关键机制和实验证据，再删除重复内容；导航负责选读，正文负责讲懂。**

## 范围与周期

先区分主动发现与固定候选整理。后者保留用户集合，不擅自补篇。主动发现先确定方向、来源、时间窗、时区和报告标识：
- 日报 `YYYY-MM-DD`；周报 `YYYY-Www`（ISO 周、周号两位）；月报 `YYYY-Mm`（自然月、月份不补零）。
- 默认使用用户时区；本项目默认 Asia/Shanghai。显式日期优先。当前周/月截止实际运行时刻，历史周期覆盖完整区间。未来周期停止并说明参数不成立。
- 周期自动任务默认上一完整自然周/月；交互中的“本周/本月”指当前周期。每次从运行日期计算，不沿用旧报告日期。
- 同名 HTML 已存在时，只有范围、证据新鲜度、内容标准均满足且未要求修订才复用。当前周期有新增覆盖或用户要求更新时补写原文件。用户要求前后对比时保留原稿，在独立评审目录保存同名的新旧版本与差异说明，不能覆盖待比较基线。

用户点名的方向是硬边界，不扩展相邻栏目。默认方向为 VLM/多模态、OCR/文档理解、RL、VLA、世界模型、基座/LLM、Diffusion LLM。“Diffusion”按文本/token 去噪理解，除非明确要求视觉扩散。长期增删方向须同步 directions 与 fetch_content.py 的 DIRECTIONS。

严格 HF-only 时，目标日期的 HF Daily Papers 是候选集边界；arXiv/PDF/项目页只用于核验。记录逐日实际有内容的日期。当前日未更新时使用区间内最近有内容日期；整个区间为空时可按既定 HF 回退策略取此前最近有内容日期，但必须在副标题明示实际覆盖日期和空窗，不能声称它属于目标时段。用户禁止跨日期时不回退。

## 发现与来源状态

从 skill 根目录执行适当命令：

```bash
python3 scripts/fetch_content.py --range today -o /tmp/paperstudio-radar.json
python3 scripts/fetch_content.py --range week --top-k 40 -o /tmp/paperstudio-radar.json
python3 scripts/fetch_content.py --start YYYY-MM-DD --end YYYY-MM-DD -o /tmp/paperstudio-radar.json
```

候选上限只是召回参数，不是完整覆盖保证；请求穷尽发现时按日期拆批并核对分页/截断。脚本只做发现、规范化、宽召回和去重，语义判断与回源阅读由模型完成。

| 来源 | 用途 | 状态处理 |
| --- | --- | --- |
| HF Daily Papers | 当期候选、社区热度 | 记录查询日期、实际覆盖日期、upvotes 与抓取时刻 |
| arXiv/论文项目页 | 身份、版本、正文与官方资料 | 核对正文及必要附录，不以元数据替代方法阅读 |
| 量子位 | 中文报道与背景 | 可用公开 RSS；技术论断回源 |
| 机器之心 | 中文报道与背景 | 使用已授权 feed；未配置写 not_configured |
| 其他 RSS/公开文章 | 用户配置的发现入口 | 记录成功、失败或搜索补充，不能静默漏源 |

使用 `--feed "名称=URL"`、`--jiqizhixin-rss` 或 `PAPERSTUDIO_JIQIZHIXIN_RSS` 接入授权来源。无稳定公开 feed 时可用用户文章或搜索补充，标 search fallback；不绕过访问控制。每个请求来源保留 success / not_configured / error 与必要原因，不因一个来源失败停止全部任务，也不声称全源覆盖。

## 筛选与证据

按 directions 逐条核验：真正的任务、贡献、去噪/动作/监督对象、主方向和次方向。关键词命中只作召回。RL 只在背景出现、视觉扩散误入文本扩散、仅感知却标 VLA 等情况排除。

对候选记录 keep/drop、primary_direction、why_match、why_read、evidence_level。按身份与版本跨源去重，一项工作只在主方向出现一次；其他方向用交叉链接。HF 热度表示关注，不等于创新与研究价值。

技术判断以论文/技术报告、官方项目和代码为依据，媒体只用于背景与观点。记录核验过的开放状态和日期；未运行代码不能写复现成功。来源冲突标明版本或口径，不自行拼接。

选择数量服从相关性、贡献和证据质量，不凑满配额。用户指定及正式入选的篇目完整覆盖，不能为了报告长度删掉后几篇。只有摘要/媒体的自选条目放观察区，不计为已完成解读；用户指定材料不足的论文保留位置、解释已知内容与缺口。

## 逐篇正文

默认读者具有编程和机器学习基础，但不了解本篇新机制；沿用用户已明确的背景。先按 [radar-writing.md](radar-writing.md) 执行“确定篇目 → 逐篇备课 → 方法与实验写作 → 复述及证据检查 → 保存正文 → 整期合并”。阅读引言、最相关前作、方法、主实验、消融/诊断与限制，必要时回查附录；初筛摘要不能直接充当正文材料。

篇首保留身份/版本、方向/任务、关键词、问题签名、来源及实际覆盖。每篇正文默认按以下五部分展开，主标题可贴合论文自然措辞：

1. **背景介绍**：必要的任务情境、输入输出和场景约束。
2. **问题及解决思路**：连起前作怎样做、卡在哪里、导致什么后果，再说明作者为什么改变某个环节，区分新机制与沿用内容。
3. **方法**：重点展开输入到输出的关键操作与连接，适用时分训练/推理、数据/监督/目标；解释设计理由并在难点处保留必要例子、公式和原图导读。
4. **实验及结果**：用“关键结果”“关键消融与分析”等小节分别解释整体效果与设计证据。交代任务、对照、指标方向、关键原始值、预算/协议、出处和支持范围，保留负结果、成本及归因限制。理论、数据、评测或综述使用“理论结果与分析”等相应标题，不虚构实验。
5. **总结**：简明收束贡献、发现、可借鉴内容与迁移条件，说明尚未验证的范围；不重复整段方法与全部分数。

在方法首次用到关键术语或缩写时，用短句解释它在本篇操作链中的具体作用。训练解读至少让读者知道：监督告诉模型什么、哪些参数因此改变、目标鼓励哪种输出行为；仅列出算法缩写、损失名称和“训练/冻结”不足以完成解释。只补理解所需的概念，不另堆术语百科，也不补造原文未给的配置。检查时临时遮掉术语名称，剩下的对象、动作与连接仍应能说明该步在做什么。

图表若同时使用主结果、消融或不同小节的数据，图注标全各项承重来源，不用单一表号覆盖来自别处的基线数值。

保持五部分的阅读顺序，不要求标题逐字一致；问题与思路在同一部分自然衔接，方法与结果内部可按论文增加小标题。以自然段落解释设计理由、状态变化和步骤连接；关键机制需要例子、公式或分步推演时，默认展开到读者能复述，不以用户另说“详细”为前提。背景介绍、问题及解决思路与总结保持简明，新增篇幅主要用于方法与关键结果。全文逐段带读、无关推导和复现配置按需求提供。所有正文都保留自身总结；Top picks 仅表示阅读顺序。

不设默认单篇/全报告字数、屏数、方法步骤数。完成理解链决定何时结束；篇幅增加本身不证明质量改善。单次输出受限时继续逐篇保存，最终从已检查正文合并，不能在合并时为适应总长度把后几篇重写为短卡。

## 报告组织与交付

逐篇正文完成后再写整期导览。开头给标题、目标与实际覆盖、时区、来源状态、总览和建议阅读顺序；正文按主方向分组，每篇独立锚点，末尾给有证据的本期回顾与观察区。方向内存在共同问题时，比较各篇改变的环节、前提与代价；不能把共享标签当作同一任务或直接继承。没有命中的方向不建空章节，也不能从当期小样本直接推断整个领域升温。

周报重点交代本周新增的机制和证据；月报复用同版本已核验记录，补充跨周路线、条件差异和有证据的认识变化，同时保留逐篇完整正文。引用旧论文建立背景时标明其时间与用途，不计作本期新发现。没有足够可比证据时直接说明关系待核，不强写趋势或胜负。

导航卡只承担选读入口，短是合理的；完整正文默认展开。避免 line-clamp、固定高度或折叠隐藏方法。使用 layout-patterns 的正文骨架，按实际章节生成目录。内部筛选日志、测试记录不混进读者正文。

输出 `{REPORT_KEY}-radar.html`，默认同 stem 的 `.wechat.md`。发现清单 JSON 是工作溯源，不是必须交付文件；用户只要 HTML 时保留临时清单即可。图片内嵌 base64，SVG 内联，必要公式离线渲染。运行 embed_images.py、validate_html.py 并检查桌面/手机显示；语义完整性另行逐篇验收。

公众号版覆盖同一批论文与八项主线，逐篇沿相同的五部分阅读顺序组织，标题可自然措辞；删重复和外围内容，不删关键条件，不以公众号长度反向限制 HTML。

## 定期运行

只有用户要求周期任务才创建/更新 automation。编辑 skill 不自动修改既有任务。更新时先读取任务清单和现有配置，保留名称、启停状态、时间、时区、方向、来源、输出位置及其他无关设置；按各自任务使用相应 skill，不把全部任务都改成雷达。

“最新 skill”应绑定到用户认可的安装源或 Git 分支：每次执行开始时读取该来源的最新完整技能包及引用资源，记录实际版本/提交，不能沿用任务创建时复制的旧正文。若使用 Git 工作副本，应在执行前正常更新到配置分支的最新版本，保留用户本地改动；来源不可用时报告未能更新，不静默宣称已用最新版。用户尚未要求合并的评审分支不能自动改指 main。

模型必须写入任务系统实际的模型字段；用户指定 6.1 sol 时，选择系统支持的 **GPT-6.1 Sol / `gpt-6.1-sol`**。只在提示词中写模型名不能切换执行模型。保存后重新读取配置，核对模型和 skill 绑定；没有管理接口时明确哪些设置尚未生效，不用仓库说明文件代替已更新任务。下列正文只描述执行内容，不能代替调度器的模型、时间和 skill 来源字段：

```text
开始执行时，读取任务所绑定来源的最新完整 $paper-studio 及其引用资源，记录实际版本。
使用 radar 流程，范围为 {今天/上一完整自然周/上一完整自然月/指定区间}，
时区 {用户时区}，方向 {用户方向}，候选来源 {来源边界}。
先计算周期名与实际覆盖，报告各来源状态，按 directions 语义精筛并跨源去重。
读取 paper-storyline、radar、radar-writing、per-paper-deep-read；按当前 skill 的正文组织，
默认是背景介绍 → 问题及解决思路 → 方法 → 实验及结果 → 总结，允许自然标题；
方向与来源在篇首，主结果与关键消融/分析分别呈现，总结保留迁移前提与整体边界。
问题与思路连贯讲述，新增讲解主要展开方法与关键结果。
逐篇备课，先写方法与实验，再做复述和证据检查、保存正文；全部完成后合并并写导览。
关键机制默认展开到可独立理解；不按篇数平摊字数，不只详读 Top picks。
原文不足项明确标注，用户指定项保留，自选观察项不冒充完整解读。
输出 {REPORT_KEY}-radar.html，按用户格式要求提供同 stem 的公众号 Markdown。
核对内容与来源，再运行图片/HTML 校验并检查视觉效果；保存完整合并稿。
```

## 验收

确认时间/候选/方向边界、来源状态与版本真实。核对五部分的实际职责与阅读顺序，不要求标题逐字匹配；问题能自然引出解决思路，主结果与消融在结果部分分别可找。按 radar-writing 记录每篇复述中的具体操作与实验判断，再回材料核对；无法恢复关键步骤时定位断点并补读或重写，材料不足则保留可见缺口。合并后核对候选清单、正文、原图和伴随稿的逐篇一致性，尤其检查中后段是否完整。主线覆盖、证据忠实、讲解可理解性分别判断；文件校验、标题齐全或篇幅变长都不能替代内容验收。

## 逐篇原图验收

遵守 [core-figures.md](core-figures.md)：每篇正式解读核查并保留适用核心原图，或在该篇给出可追溯的缺图/不适用说明。教学SVG不默默替代原图；不以全报告图数或体积限额省略主图。HTML 必须运行 `validate_html.py output.html --require-core-figures`，并逐篇人工回源与看图。
